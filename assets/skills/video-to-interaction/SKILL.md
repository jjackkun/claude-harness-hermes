# video-to-interaction — 참고 영상을 전부 보고, 그 움직임을 만든다

## 왜 만들었나

2026-10-21, 티켓 찢기 영상(14초)을 0.5초 간격으로만 보고 두 번 만들었다가 "영상과 달라", "대충 보지마" 를 들었다.
0.1초 간격 143장을 전부 보고 원본 해상도로 확대하자 그제야 보였다 — 찢기는 앞선 아래 흰 종이 안에서 벌어지는 구멍,
끈적하게 녹아 붙는 면, 떨어진 조각을 손에 들고 다니기. 그 판은 "너무 잘되었다" 로 승인됐다.
다음 날 23.6초 영상은 처음부터 236장 전수로 보고 천 물리·뒤집기·찢기를 한 번에 만들어 "와 대박대박" 을 들었다.

**핵심 효과는 0.3초 안에 지나간다.** 띄엄띄엄 보면 그 사이를 상상으로 메우게 되고, 상상은 영상과 다르다.
그래서 이 스킬은 전수를 다 보기 전에는 코드를 쓰지 않게 한다.

## ① 영상 확인

```bash
S=<이 스킬 폴더>/scripts/video_frames.sh
bash $S probe "<영상>"                 # 길이 · 크기 · fps
bash $S full  "<영상>" .harness/out/<주제>-video   # 1초 간격 전체 화면 → 자를 범위 정하기
```

- 출력은 git 이 무시하는 폴더(`.harness/out/` 등)에 둔다. 영상 원본은 사용자가 둔 자리 그대로 쓴다
- ffmpeg 는 스크립트가 찾는다(시스템 것 → 없으면 `uv` 로 프로젝트 안 캐시). **전역 설치를 먼저 권하지 않는다.**
  Playwright 내장 ffmpeg 는 H.264 를 못 풀어 쓸 수 없다
- 사용자가 "영상의 오른쪽" 처럼 범위를 말하면 그 범위가 기준이다. 전체 화면 몇 장을 보고 UI 가 있는 사각형을 자르기 값(`폭:높이:x:y`)으로 정한다
- 확인할 것: 사용자가 원하는 **동작이 무엇인지 한 줄로** (예: "드래그로 움직이고, 뒤집고, 하단 티켓 뜯기"). 모호하면 이때 한 번만 묻는다

## ② 전수 추출 — 10fps, 8장 묶음, 전부 읽기

```bash
bash $S sheets "<영상>" .harness/out/<주제>-video "<자르기>"   # 프레임 전부 + 8장 묶음
```

- 묶음 n 은 0.8초 × (n−1) 부터 시작, 왼쪽→오른쪽·위→아래. **묶음을 하나도 건너뛰지 않고 전부** 읽는다
- 처음 사용자에게 몇 fps 로 볼지 확인받는 것도 좋다 — 사용자는 이 숫자를 기억하고 묻는다(10-22 "어제 몇 프레임으로 쪼갰지?")
- 읽으면서 시간대별로 적는다: "0~4.8초 끌기 — 잡은 점이 손을 따라오고 천처럼 접힘, 놓으면 출렁이다 평평"
- 끝부분이 처음 장면과 같으면 영상이 되풀이되는 것 — 그렇게 적고 넘어간다

## ③ 확대 — 핵심 순간은 원본 해상도로

```bash
bash $S zoom .harness/out/<주제>-video <시작 프레임> <장 수> "<자르기>" <이름>
```

- 묶음에서 "뭔가 일어나는" 구간(찢김·뒤집힘·붙음·튕김)을 골라 원본 해상도로 다시 본다. 장 수는 12~16 이 한 번에 읽기 좋다
- 확대에서 보이는 것: 가장자리 모양(톱니·구멍 반쪽), 어느 쪽부터 시작하는지, 조각이 뒤집혀 뒷면이 보이는지, 진행 표시(%)

## ④ 관찰 기록 — "본 것" 을 문서에

[references/observation.md](references/observation.md) 양식으로 프로젝트의 디자인 참고 문서(예 `docs/design-docs/design/references.md`)에 남긴다.

- **본 것**(시간 · 무엇이 어떻게) / **가져올 것** / **가져오지 않을 것**(프로젝트 색·글꼴 규칙과 맞지 않는 것, 우리 데이터에 없는 것 — QR·바코드처럼 그리면 지어낸 정보가 되는 것)
- 사용자 요청이 영상과 다르면 **요청이 이긴다** (예 10-21 "당기는 방향 아무렇게나", 10-22 "하단에 티켓 뜯기")
- 이 기록이 있어야 다음 세션이 영상을 다시 보지 않고 이어 간다

## ⑤ 기법 고르기 · 구현

[references/techniques.md](references/techniques.md) 에서 움직임 종류에 맞는 기법을 고른다 (평면 스프링 · SVG 끈적임 · 천 물리 Verlet+WebGL).
천처럼 휘는 면이면 [assets/cloth/](assets/cloth/) 의 `cloth.js`·`render.js` 를 출발점으로 쓴다.

- 승인용 미리보기는 프로젝트 규칙의 자리에(예 `docs/design-docs/design/previews/<날짜-주제>/` 폴더 하나), 프로젝트 디자인 토큰으로
- **file:// 로 열린다고 가정한다** — 사용자는 `\\wsl.localhost\...` 경로를 브라우저에 붙여 연다. ES 모듈(`type="module"`)·fetch 는 막힌다 → 보통 `<script src>` + 이름공간(`window.XX`)
- 값은 지어내지 않는다: 화면 문구·금액은 프로젝트 문서의 예시 값을 쓰고 출처를 페이지에 밝힌다
- 키보드·동작 줄이기(`prefers-reduced-motion`) 대체 수단을 하나 둔다 (예 "떼기 시연" 단추, 즉시 뒤집기)
- 한 파일 한 책임: 그림(텍스처) · 물리 · 그리기 · 잇기(포인터·단추·상태)

## ⑥ 검증 — 수치로, 그리고 영상 같은 순간과 나란히

[references/verification.md](references/verification.md) 대로 Playwright 스크립트를 미리보기 폴더 `check/` 에 둔다.

- 주장마다 수치 하나: "끌면 접힌다" → 면 깊이 0 → 70px, "놓으면 돌아온다" → 3초 뒤 0px, "끝까지 당기면 찢긴다" → 100% + 상태 문구
- 콘솔 오류 0, 라이트·다크 × 프로젝트 휴대폰 크기 스크린숏
- 스크린숏을 영상의 같은 순간 프레임과 **나란히** 놓고 본다 — 다르면 고친다. 헤드리스 WebGL 은 초당 12~13프레임이라 중간 동작은 연속 촬영으로 잡는다
- 수치가 실패하면 원인을 찾아 고치고 그 이유를 상수 옆 주석과 계획서 결정 로그에 남긴다 (10-22: 절취 고리 굳기 · 마지막 칸 경첩 · 판처럼 도는 뒤집기 — 세 번 다 검증이 잡았다)

## ⑦ 보고

- 첫 줄: 연 경로(사용자가 여는 방식 그대로 — WSL 이면 `\\wsl.localhost\<배포판>\...`)
- 구현한 동작(영상의 어느 장면에 해당하는지) · 검증 수치 · 영상과 다르게 한 것과 이유
- 사용자 판정이 필요한 것(승인·고칠 점)으로 끝낸다. 승인 기록은 사용자가 승인이라고 말한 뒤에만 남긴다

## 함정 (실제로 부딪힌 것)

| 증상 | 원인 | 처방 |
|---|---|---|
| 영상과 "달라" 를 두 번 들음 | 0.5초 간격으로 봄 | 10fps 전수 + 확대 |
| ffmpeg 가 H.264 를 못 품 | Playwright 내장 ffmpeg | `video_frames.sh ffmpeg` (uv 캐시) |
| 묶음 한 장 쓰기가 "같은 이름에 여러 파일" 오류 | tile 출력이 여러 프레임 | `select='lt(n,N)'` + `-frames:v 1 -update 1` (스크립트에 들어 있음) |
| 미리보기가 사용자 화면에서 빈 화면 | file:// 에서 ES 모듈 막힘 | 보통 스크립트 + 이름공간 |
| Playwright 가 브라우저 없다고 함 | 버전별 브라우저가 프로젝트 안 폴더에 | 프로젝트 e2e 설정의 `PLAYWRIGHT_BROWSERS_PATH` 를 따라 쓴다 |
| 천 물리·찢기 튜닝 함정 | — | [references/techniques.md](references/techniques.md) 「천 물리 함정」 |
