# prd-writer — 결정 가능한 PRD

PRD 는 "무엇을 왜 만들고, 다 됐는지 어떻게 아는가" 를 한 장에 못 박는 문서다.
이 문서가 다음 단계의 입력이 된다: 시안(ui-prototype)은 요구를 화면으로, 실행 계획서는 요구를 목표로, 의도 대조(intended-vs-implemented)는 요구를 코드와 맞춘다.
그래서 **요구마다 번호와 검증 방법**이 있어야 하고, **지어낸 사실이 없어야** 한다 — 하류가 지어낸 숫자를 사실로 받아 화면과 코드에 박기 때문이다.

계약: `references/contract.md` (contract-version: 1) — 폴더·이름·필수 칸·FR 규칙의 정본. 이 문서에 규칙을 다시 적지 않는다.

## 흐름

### ① 어느 기획인가

계약 §3(고르기)·§4(찾기 순서)대로 기획 폴더를 정한다.
새 기획이면 계약 §2 규칙으로 `<이름>` 을 제안하고 확인받는다. 이미 있는 폴더면 "이어 쓸지 / 새 이름인지" 묻는다.
이미 prd.md 가 있으면 **새로 쓰지 않고 고친다** (§⑤ 갱신).

### ② 가진 것부터 읽는다

- `docs/product-specs/<이름>/brief.md` — 있으면 문제·대상·가장 좁은 시작점·대안·가정을 그대로 가져온다. `verdict: 보류` 면 쓰기 전에 "점검에서 보류로 판정된 기획입니다" 를 먼저 알리고 진행할지 묻는다.
- 옛 위치의 기획서·화면 흐름 문서, 사용자가 댄 파일 (계약 §4).
- 문서를 읽었으면 무엇을 읽었는지 한 줄로 보인다.

### ③ 빈 곳만 묻는다 — 최대 3개, 한 번에

문제·대상 사용자·목표 지표 중 비어 있는 것만 묻는다. **사용자만 아는 것**(문제를 겪는다는 근거, 실제 사용자, 성공의 기준)만 묻고, 찾아볼 수 있는 것은 묻지 않는다.
질문한 답장에는 PRD 를 쓰지 않는다. 사용자가 "그냥 써" 라고 하면 빈 곳을 「가정」 으로 표시하고 쓴다.
왜 셋인가: 넷 이상이면 답이 짧아지고, 하나씩 물으면 왕복이 늘어난다.

### ④ 쓴다

`references/prd-template.md` 를 복사해 채운다. 짧게 — 한두 쪽이 기본이고, 사용자가 원할 때만 길게.

- **요구사항 표**: 사용자가 얻는 것 한 줄 = 한 행. 구현 방법(테이블·컴포넌트 이름)은 요구가 아니다.
  검증 칸에는 "누가 무엇을 해 보면 무엇이 보인다" 를 쓴다. 검증을 쓸 수 없는 요구는 아직 요구가 아니다 — 「열린 질문」 으로 보낸다.
- **우선순위**: 첫 버전에 없으면 안 되는 것만 `필수`. 다 `필수` 면 아무것도 우선이 아니다.
- **비범위**: 첫 버전에서 일부러 안 하는 것. 범위만큼 중요하다 — 시안과 계획서가 범위를 넘지 않게 막는다.
- **실행 계약**: 문서를 읽고 혼자 구현할 사람(다음 세션의 에이전트 포함)이 추측하지 않게 — 정본 문서, 손대지 말 것, 막히면 누구에게 묻는가.
- **지어내지 않기**: 문서·사용자 답에 없는 숫자·사실(사용자 수, 가격, 기한)은 본문에 쓰지 않고 「가정·열린 질문」 에 "가정:" 으로 적는다.
- 말은 쉽게, 문장은 짧게. 약어는 처음 나올 때 푼다.

### ⑤ 갱신

계약 §6·§7: 제자리에서 고치고 `updated` 를 바꾼다. FR 번호는 다시 쓰지 않는다 — 지운 요구는 행을 남기고 `폐기`.
`approved` 문서를 고치면 `draft` 로 내리고 바뀐 FR 을 보고한다.

### ⑥ 검사하고 끝낸다

```bash
python3 <이 스킬>/scripts/check_prd.py docs/product-specs/<이름>/prd.md
```

종료 0 이 아니면 표식(`[절 없음]`·`[검증 빈칸]`·`[FR 중복]` …)대로 고치고 다시 돈다. 통과하기 전에는 끝났다고 말하지 않는다.

## 보고

- 남긴 파일 경로, FR 수(필수 몇 개), 「가정」 수.
- 일부러 뺀 것 한 줄 (예: 경쟁 분석, 상세 화면 흐름) — 사용자가 늘려 달라고 할 수 있게.

다음: "시안 만들어" 라고 하시면 이 PRD 로 눌러 보는 화면을 만들고, "구현 계획 세우자" 라고 하시면 FR 번호를 목표로 옮긴 실행 계획서를 씁니다.

## 기존 PRD 검토

"PRD 검토해 줘" 면 쓰지 않고 본다: `check_prd.py` 결과 → 첫 버전 결정을 막는 빈칸 → 가정으로 표시 안 된 단정 → 빼도 되는 것. 빈칸을 먼저, 뺄 것을 나중에.
계약 밖 문서(옛 위치, FR 없음)면 계약 §8 대로 절 제목·줄 번호로 짚고 "계약 형식으로 옮길까요" 를 한 번 묻는다.
