# slow-spot — 재고, 하나만 고치고, 원래 결과와 대조한다

## 왜 있나

어느 설치 스크립트가 1회 14초였다. 처음에는 매 도구 호출마다 도는 훅을 의심했다. 재 보니 훅은 모두 0.12초 아래였다.
줄 단위로 재자 범인은 설치 안의 함수 하나(`manifest_add`)였다. 설치 시간의 55%였고, python 을 347번 띄웠다.
그 함수만 고쳐 14초가 8초가 됐다. 고치기 전 결과 432개 파일과 바이트까지 같은지 대조한 뒤에 남겼다.
같은 절차로 시험 하나도 83초 → 15초가 됐다 — 범인은 시험마다 같은 설치를 9번 하던 것이었다.

느린 곳은 짐작과 다른 곳에 있다. 그리고 빠르게 만든 코드는 조용히 다른 답을 낸다. 그래서 순서를 지킨다.

## ① 무엇이 느린지 숫자로 정한다

- 사용자가 기다리는 명령 하나를 고른다(설치·시험 하나·빌드·CLI). 추적 없이 3번 재서 가운데 값을 적는다 — 이것이 "이전" 값이다.
- 여러 후보가 있으면 각각 한 번씩 재서 가장 긴 것부터 본다. 백그라운드로 도는 일(사용자가 기다리지 않는 일)은 뒤로 미룬다.
- 시험 묶음이 병렬로 돌면 전체 시간은 **가장 긴 시험 하나**가 정한다. 합계가 아니라 그 하나를 본다.

## ② 프로파일로 범인을 찾는다

bash:

```bash
S=<이 스킬 폴더>/scripts
bash $S/bash_profile.sh .harness/out/slow.trace <스크립트> [인자...]
python3 $S/trace_agg.py .harness/out/slow.trace --top 15
```

- 세 표를 읽는다. **함수별**(어느 함수) → **줄별**(그 안 어느 줄) → **명령별**(같은 외부 명령이 몇 번 불렸나).
- 명령별 표에 `python3 ×347` 처럼 외부 명령이 수백 번 보이면, 계산이 아니라 **프로세스 기동 횟수**가 원인이다.
  이때는 언어를 바꿔도 줄지 않는다. 호출을 묶어야 줄어든다.
- `bash 다른.sh` 로 띄운 자식 스크립트는 추적되지 않는다. 자식이 범인으로 보이면 그 자식을 따로 잰다.
- xtrace 는 전체를 1.1~1.3배 느리게 만든다. 순위는 추적으로 보고, 시간은 ①·⑤처럼 추적 없이 잰다.

Python·Node: `references/profilers.md` 의 명령을 쓴다(cProfile · `-X importtime` · `node --cpu-prof`).

**1위가 전체의 20% 아래면** 고칠 곳 하나가 없다는 뜻이다. "고르게 퍼짐" 이라고 보고하고 멈춘다.
여러 군데를 조금씩 고치는 일은 결과 대조 비용만 늘린다.

## ③ 고치기 전에 기준선을 찍는다

고칠 함수가 만들어 내는 결과(파일·폴더·출력)를 정하고, 같은 입력으로 **두 번** 찍는다.

```bash
python3 $S/snapshot.py take <결과 폴더> .harness/out/before1.snap
# 같은 입력으로 한 번 더 돌린 뒤
python3 $S/snapshot.py take <결과 폴더> .harness/out/before2.snap
python3 $S/snapshot.py diff .harness/out/before1.snap .harness/out/before2.snap
```

- 두 기준선 사이에 다른 경로가 **잡음**이다(시각·무작위 ID·백업 폴더 이름). 잡음은 프로젝트마다 다르므로 정해진 목록이 없다.
  이 단계에서 찾은 경로만 `--ignore <정규식>` 으로 넘긴다. 잡음이 아닌 것을 무시 목록에 넣으면 결함을 덮는다.
- 결과가 폴더가 아니면(표준 출력·DB 줄) 그 출력을 파일로 받아 같은 방법으로 찍는다.
- 장면을 여러 개 찍는다: 처음 실행 · 다시 실행 · 사용자가 고친 상태에서 실행 · 이상한 이름(공백·탭·한글).

## ④ 범인 하나만 고친다

- ②에서 1위인 함수 하나만 바꾼다. 주변 코드는 손대지 않는다.
- 바깥 동작(인자·출력·종료 코드·파일 형식)은 그대로 둔다. 바뀌어야 한다면 이 스킬의 범위가 아니다 — 사용자에게 알린다.
- 고친 함수를 직접 부르는 다른 쪽(시험·다른 스크립트)이 있으면, 그쪽 동작이 예전과 같은지도 본다.

## ⑤ 대조하고 잰다 — 같을 때만 남긴다

```bash
python3 $S/snapshot.py take <결과 폴더> .harness/out/after.snap
python3 $S/snapshot.py diff .harness/out/before1.snap .harness/out/after.snap --ignore '<잡음>' ...
```

- 종료 0(다른 경로 0)이어야 남긴다. 하나라도 다르면 원인을 찾을 때까지 남기지 않는다.
- 추적 없이 3번 재서 "이전 → 지금" 을 적는다. 빨라지지 않았으면 되돌린다.
- 관련 시험을 돌린다. 새로 만든 동작(예: 묶음 모드)에는 시험을 더한다.

## ⑥ 보고

- 첫 줄: "X 가 A초 → B초" (같은 기계, 추적 없이, 몇 번 잰 가운데 값).
- 범인: 함수 이름 · 비중(%) · 호출 횟수 · 원인 한 줄.
- 대조: 장면 수 · 파일 수 · 무시한 잡음 경로.
- 고치지 않은 것과 그 이유(예: 2위 함수 12% — 고르게 퍼짐).

## 하지 않는 것

- 재지 않고 고치기. "이 부분이 느릴 것 같다" 로 시작하지 않는다.
- 범인이 아닌 곳을 같이 "정리"하기.
- 대조 없이 "빨라졌습니다" 라고 보고하기.
- 추적 파일(`.trace`)을 커밋하거나 공유하기 — xtrace 는 펼친 명령을 그대로 적어 비밀값이 남을 수 있다. `.harness/out/` 에만 둔다.
- 다른 언어로 다시 쓰기를 먼저 제안하기. 원인이 계산일 때만, 그리고 ②가 그것을 보일 때만 꺼낸다.
