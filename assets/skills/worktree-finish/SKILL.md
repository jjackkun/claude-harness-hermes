# worktree-finish — 끝낸 worktree 를 main 에 합치고 지운다

## 왜 있나

데스크톱 앱은 세션마다 worktree 를 만든다. 일을 끝내도 브랜치가 main 에 합쳐지지 않으면 세 가지가 생긴다.

- 사용자가 main 에서 결과를 볼 수 없다.
- 다른 세션이 같은 일을 다시 한다. 2026-11-19 jj-agent-room 에서 결재 A3 를 두 세션이 따로 만들었다.
- worktree 가 쌓인다. 2026-11-20 에는 6개가 남아 있었고, 그중 3개에 main 에 없는 커밋이 있었다.

사용자는 혼자 일한다. 그래서 PR 을 쓰지 않고 로컬 main 에 바로 합친다. 푸시는 사용자가 따로 시킬 때만 한다.

## 흐름

### ① 끝났는지 본다

계획서의 §2 목표가 모두 확인됐고, 시험이 통과했는지 본다. 끝나지 않았으면 이 스킬을 쓰지 않는다. 중간 커밋은 평소처럼 한다.

Step 하나를 끝낸 것은 계획이 끝난 것이 아니다. 이 worktree 가 건드린 계획서의 §2 에 `[ ]` 가 남았거나 기획서(`prd.md`)가 `approved` 가 아니면, 스크립트가 아무것도 바꾸지 않고 24 로 멈춘다(2026-11-25 jj-agent-room: Step 하나 뒤에 worktree 를 지웠다).

사용자가 "지금 main 에 넣어" 라고 했는데 계획이 아직 열려 있으면 `--keep-worktree` 를 준다. 합치기까지만 하고 worktree · 브랜치는 남긴다.

### ② 스크립트를 부른다

셸 위치는 worktree 안에 둔 채로, **이 스킬의 기준 폴더**(스킬을 불렀을 때 보이는 `Base directory`)의 `scripts/finish.sh` 를 부른다. 커밋 안 된 변경이 있으면 커밋 메시지를 준다. 커밋 게이트(pre-commit)는 그대로 돈다.

```bash
bash <기준 폴더>/scripts/finish.sh --message "<type>: <요약>"
```

worktree 안의 상대 경로(`.claude/skills/...`)로 부르지 않는다. 설치된 스킬을 git 이 무시하는 저장소에서는 worktree 에 이 파일이 없다(2026-11-20 jj-agent-room 복제본 실측). 메인 브랜치 이름이 `main` 이 아니면 `--main <이름>` 을 준다.

스크립트가 하는 일:
1. 멈춤 조건을 검사한다(아래 표).
2. 커밋한다.
3. main 의 지금 해시를 출력한다(되돌릴 때 쓴다).
4. main 위로 rebase 한다.
5. 메인 체크아웃에서 `merge --ff-only` 로 합친다.
6. 셸 위치를 메인 체크아웃으로 옮긴다.
7. worktree 를 지운다.
8. 브랜치를 지운다(`branch -d`).

`--keep-worktree` 이면 5 다음 사후 확인까지만 하고 6~8 을 건너뛴다.

### ③ 결과를 읽는다

- 끝 줄이 `result: merged <브랜치> into main (<이전>..<이후>), removed <경로>` 이면 끝이다.
- 이 세션의 작업 폴더가 사라졌다. 다음 명령은 메인 체크아웃 경로로 부른다.
- 끝 줄이 `…, kept <경로>` 이면(`--keep-worktree`) 합치기만 끝났다. 작업 폴더는 그대로다. 계획의 다음 Step 을 이어 한다.
- 보고에 합친 커밋 범위와 "푸시하지 않음" 을 쓴다.

### ④ 멈췄으면

스크립트는 `stopped(<코드>): <이유>` 와 다음 할 일을 출력한다. 우회 플래그(`--force` · `-D` · `--no-verify`)로 밀어붙이지 않는다. 막힌 이유는 대개 다른 세션의 작업이나 지우면 잃는 파일이기 때문이다.

| 코드 | 뜻 | 할 일 |
|---|---|---|
| 10 | 메인 체크아웃에서 불렀다 | worktree 세션에서만 쓴다 |
| 11 | 메인 체크아웃이 main 이 아닌 브랜치에 있다(처음, 또는 합치기 직전에 바뀜) | 메인을 쓰는 세션이 있을 수 있다. 사용자에게 묻는다 |
| 12 | detached HEAD 이거나 브랜치가 main 자신이다 | `git switch -c <브랜치>` 뒤 다시 부른다 |
| 13 | 브랜치가 원격에 있다 | rebase 가 해시를 바꾼다. 합칠 방법을 사용자에게 묻는다 |
| 14 | 메인 체크아웃의 커밋 안 된 변경이 합칠 파일과 겹친다 | 그 변경의 주인 세션이 커밋한 뒤 다시 부른다. 남의 변경을 옮기지 않는다 |
| 15 | rebase 가 실패했다(브랜치는 rebase 전으로 되돌려짐). git 의 오류 문구가 함께 나온다 | 충돌이면 풀고 다시 부른다 |
| 16 | 커밋 게이트가 막았다 | 게이트 메시지를 고친다 |
| 17 | main 이 계속 움직여 두 번 합치지 못했다 | 잠시 뒤 다시 부른다 |
| 18 | 지우면 잃는 무시 파일이 있다(예: `server/uploads/`) | 목록을 사용자에게 보이고, 옮기거나 백업한 뒤 다시 부른다 |
| 19 | worktree 지우기나 `branch -d` 가 거부됐다(합치기는 끝남) | `git worktree list` 를 보이고 사용자에게 넘긴다 |
| 20 | 다른 마무리가 진행 중이다(잠금) | 그 세션이 끝난 뒤 다시 부른다. 잠금을 지우지 않는다 |
| 21 | main 은 그대로인데 ff 가 거부됐다 | git 의 오류 문구를 사용자에게 보인다 |
| 22 | 커밋 안 된 변경이 있는데 `--message` 가 없다 | 메시지를 주고 다시 부른다 |
| 23 | 합친 뒤 main 이 브랜치 끝에 있지 않다(아무것도 지우지 않음) | `git log` 를 보이고 사용자에게 넘긴다 |
| 24 | 이 worktree 의 계획서 §2 에 `[ ]` 가 남았거나(§2 절 · 체크 항목이 없거나 코드 펜스가 닫히지 않은 것도 같다) 기획서가 `approved` 가 아니다(아무것도 바꾸지 않음 — 커밋도 안 함) | 계획이 끝날 때까지 worktree 에서 커밋만 한다. 사용자가 지금 main 에 넣으라고 했으면 `--keep-worktree` 로 다시 부른다. 18 과 함께 걸리면 18 이 먼저 나온다 |

다시 만들 수 있어 지워도 되는 무시 파일: `node_modules` · `.venv` · 캐시 폴더 · 설치된 `.claude/` · `.harness/` · `.hermes/` · `.env` 심볼릭 링크. 진짜 `.env` 파일과 `.claude/settings.local.json`(그 세션에서 승인한 권한)은 지우면 잃는 파일로 본다.

게이트가 커밋을 막으면(16) 스크립트가 스테이징을 모두 푼다. 파일 내용은 그대로지만, 미리 일부만 스테이징해 두었다면 그 구분은 사라진다.

## 하지 않는 것

- 푸시·PR — 사용자가 시킬 때만 한다.
- 다른 worktree 나 다른 세션의 커밋 안 된 변경을 옮기거나 합치는 일.
- 남이 만든 잠금(`worktree-finish.lock`)을 지우는 일.

## 검증

정적 시험(모델 호출 0): `bash tests/worktree-finish-test.sh`. 임시 저장소마다 정상·멈춤 사례를 돌린다(단언 102개). 열린 문서 판정: `.venv/bin/pytest -q tests/test_open_docs.py tests/test_worktree_state.py`. 시험은 임시 폴더 안에서만 돈다.
