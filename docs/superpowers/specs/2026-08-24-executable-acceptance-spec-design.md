# R-acc — 실행 가능한 인수 조건

> 작성일: 2026-08-24
> 목적: 계획서의 "목표"를 산문이 아니라 **실행되는 검증**으로 만든다.

## 개요

영상의 Specifier 는 사람의 요구 문서를 받아 **Gherkin 인수 테스트 명세**와
UI QA 절차 문서로 변환한다. 뒤따르는 Coder·QA 에이전트는 그 명세를 통과 조건으로 삼는다.

이 저장소에는 `docs/exec-plans/` 계획 체계가 있으나 **사람이 읽는 문서이지 실행되는 명세가 아니다.**
계획과 코드의 일치는 `R-plan-stale` 이라는 **휴리스틱 경고**에만 의존한다.

## 문제 — 실측

### 1. 골격은 이미 있다

`docs/exec-plans/template.md` §2:

```text
## 2. 목표 (What — 검증 가능한 형태)
```

**"검증 가능한 형태"를 이미 요구하고 있다.** 그러나 형식이 정해져 있지 않아
자연어 문장으로 채워지고, 그 문장이 실제로 검증되는지는 아무도 확인하지 않는다.

### 2. 계획 축의 검사는 전부 "존재"만 본다

`core-beliefs.md` 의 계획 관련 3개 룰:

| 룰 | 검사 대상 | 판정 |
|---|---|---|
| `R-plan-missing` | 계획서가 **있는가** | 경고 |
| `R-plan-stale` | 계획서가 **스테이징됐는가** | 경고 |
| `R-retro` | 회고 §8 이 **비어 있지 않은가** | 경고 |

`R-retro` 의 한계 서술이 이 축 전체의 성격을 요약한다:

```text
**한계**: 기계는 "쓰지 않았음" 까지만 본다. 회고의 품질은 판정하지 않는다.
```

**목표가 달성됐는지는 어느 룰도 보지 않는다.**

## 설계

### Gherkin 을 도입하지 않는다

영상은 Gherkin 을 쓰지만 이 저장소에는 맞지 않는다.

- Gherkin 실행에는 프레임워크(`behave`, `pytest-bdd`)가 필요하다. 미설치이고,
  하네스는 여러 프로젝트에 설치되므로 프레임워크 요구는 곧 설치 실패 = 게이트 침묵이다.
- 이 저장소의 검증 수단은 이미 bash 테스트 28개다. 별도 명세 언어를 얹으면
  **검증이 두 곳으로 갈라진다** — Gherkin 시나리오와 bash 테스트가 따로 놀게 된다.

### 대신 목표에 검증 명령을 붙인다

계획서 §2 의 각 목표를 **목표 문장 + 그것을 확인하는 명령** 쌍으로 쓴다.

```markdown
## 2. 목표 (What — 검증 가능한 형태)

- [ ] 공개 심볼 8개짜리 새 파일 생성이 차단된다
      `bash tests/iface-gate-test.sh`
- [ ] 7개짜리는 통과한다
      `bash tests/iface-gate-test.sh`
- [ ] 기존 훅 회귀 없음
      `bash tests/harness-hooks-smoke.sh`
```

Gherkin 의 Given/When/Then 이 하는 일 —**"무엇이 참이어야 하는가"를 기계가 확인 가능한 형태로 적기**—
을 이 저장소의 기존 수단(bash 테스트)으로 달성한다. 새 언어도, 새 프레임워크도 없다.

### `R-acc` — 검사 규칙

| 규칙 | 내용 | 행동 |
|---|---|---|
| `R-acc-1` | `active/` 계획서 §2 의 목표 항목에 검증 명령이 없음 | 경고 |
| `R-acc-2` | `completed/` 로 옮기는데 §2 체크박스가 미완(`[ ]`) | 경고 |

**둘 다 경고다.** `R-retro` 와 같은 이유 — 기계는 "쓰지 않았음"까지만 본다.
검증 명령이 적혀 있다는 사실이 그 명령이 실제로 통과한다는 뜻은 아니다.

`R-acc-2` 는 `R-retro` 와 같은 지점에서 발화한다(`git diff --cached --diff-filter=RA`).
`R-retro` 가 §8 회고를 보는 자리에서 §2 목표도 함께 본다 — **훅을 새로 만들지 않는다.**

### 명령을 실제로 실행하지 않는 이유

계획서에 적힌 명령을 훅이 실행하면 임의 명령 실행이 된다.
계획서는 에이전트가 쓰는 파일이므로, 거기 적힌 것을 커밋 훅이 실행하는 구조는
**게이트가 게이트 대상에게 실행 권한을 넘기는 것**이다. 검사하지 않는다.

실행은 사람이나 에이전트가 하고, 훅은 "적혀 있는가 / 체크됐는가"만 본다.

## 검증

| 항목 | 방법 |
|---|---|
| `R-acc-1` | 검증 명령 없는 §2 를 스테이징 → 경고 |
| `R-acc-1` 오발화 | 명령이 붙은 §2 → 침묵 |
| `R-acc-2` | 미완 체크박스 상태로 `completed/` 이동 → 경고 |
| 템플릿 갱신 | `template.md` §2 가 새 형식을 보여주는지 |
| 회귀 | 기존 `plan-state-test.sh` 통과 |

`plan_state.py` 에 §2 파서를 추가하고 `tests/plan-state-test.sh` 를 확장한다.
**새 모듈을 만들지 않는다** — `plan_state.py` 는 이미 계획서 파싱을 담당하며
공개 심볼 7개로 `R-iface` 임계(8) 아래다. 파서 1개 추가는 그 범위 안이다.

## 미해결

1. **템플릿 변경이 기존 계획서에 미치는 영향.** `active/` 의 기존 계획서는 새 형식이 아니다.
   전부 경고를 받게 되므로, 신규 계획서에만 적용할지 일괄 갱신할지 결정이 필요하다.
2. **§2 이외 항목.** 영상의 Specifier 는 UI QA 절차 문서도 만든다.
   이 저장소는 CLI·훅 중심이라 UI QA 대상이 없으나,
   하네스가 설치되는 프로젝트에는 있다. 프로젝트별 확장 여부는 별도 판단이 필요하다.
