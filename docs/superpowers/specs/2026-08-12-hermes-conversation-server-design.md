# 헤르메스 대화 서버 — 기기 간 맥락 연속성 설계

> 작성일: 2026-08-12
> 목적: 한 기기에서 하던 대화·작업 맥락을 다른 기기에서 그대로 이어가기 위해,
> 헤르메스의 저장 바닥을 기기 로컬에서 공유 서버로 옮긴다.
> 상태: 🟡 기획 (살아있는 문서 — 결정될 때마다 갱신한다)
>
> 이 문서는 **논의 결과의 정본**이다. §4 "아직 정하지 않은 것" 이 남아 있는 동안은
> 실행 계획(`plans/`)을 쓰지 않는다.

---

## 1. 동기 (Why)

기기를 옮기면 **무엇을 왜 하다 말았는지가 사라진다.** 자산은 따라오는데 맥락이 안 따라온다.

### 관측된 사실

| # | 사실 | 확인 방법 |
|---|---|---|
| 1 | 룰·스킬·훅은 기기 간 복원된다 | 이 저장소를 `git clone` |
| 2 | 일반화된 지식은 그물망으로 이동한다 | `~/.hermes/mesh/skills/` — `scripts/hermes-search.py:15` 주석 |
| 3 | **프로젝트 작업 상태는 기기에 갇혀 있다** | `.gitignore` 에 `.hermes/` 등재 |
| 4 | 갇힌 것의 실체는 `<project>/.hermes/state.db` | `session_summary`·`session_history`·`loops` |
| 5 | 프로젝트 신원이 **폴더 이름**이다 | `assets/hooks/claude-userpromptsubmit-mistake-detect.sh:47` — `--project-id "$(basename "$project_dir")"` |

즉 헤르메스는 이미 "쓴다 → 되살린다" 구조를 갖췄다. **그 바닥이 기기 로컬일 뿐이다.**
지금은 기기마다 뇌가 따로 있는 상태이고, 이 설계는 그 갈라진 뇌를 하나로 붙인다.

### 이미 깔려 있는 관

새로 만들 것이 아니라 **목적지와 소스만 추가하면 되는** 지점들:

| 방향 | 현재 구현 | 트리거 |
|---|---|---|
| 쓰기 | `scripts/hermes-summarize.py` — 5슬롯 롤링 요약 | Stop 훅 (`claude-stop-retrospective.sh:71`) |
| 읽기(브리핑) | `scripts/hermes-recall.py --inject` — `open`+`decisions` 주입, `recall_marker` 로 세션당 1회 | UserPromptSubmit 훅 |
| 읽기(검색) | `scripts/hermes-search.py` — 프로젝트 → 전역 → 그물망 3계층, 슬롯 예산 배분 | UserPromptSubmit / PostToolUse |

특히 회상이 뽑는 두 슬롯 `open`(미해결) + `decisions`(결정)이,
사용자가 필요하다고 지목한 **"뭐 하다 말았나 / 왜 그렇게 정했나"** 와 정확히 일치한다.

## 2. 문제 정의

기기 간 연속성을 파일 복사로 풀면 복사본 관리 문제로 굴러떨어진다. 실제로 세 겹이 걸린다.

1. **경로가 신원에 박혀 있다.** 대화 로그 디렉터리가 `-home-jjackkun-PROJECT-claude-harness-hermes`
   처럼 작업 경로를 변환한 이름이다. 기기마다 경로가 다르면 못 찾는다.
2. **양쪽에서 이어가면 갈라진다.** 대화는 순서가 본질이라 병합이 성립하지 않는다.
3. **통로가 없다.** 코드 저장소에 대화 로그를 커밋할 수는 없다.

→ **원본을 하나만 두면 세 문제가 동시에 사라진다.** 그것이 서버다.

## 3. 설계 (결정된 것)

### 3.1 쓰기 — 로컬 먼저, 서버로 밀기

로컬 `state.db` 에 먼저 쓰고, 그다음 서버로 민다.

- 서버가 죽거나 네트워크가 끊겨도 그 기기의 작업은 그대로 굴러간다.
- 밀리지 못한 것은 쌓였다가 복구 시 올라간다.
- 지금 코드가 이미 로컬에 쓰므로 **기존 경로를 뜯지 않고 밀어넣기 단계만 얹는다.**

### 3.2 미는 주체는 훅이다 — MCP 가 아니다

| | 훅 | MCP 도구 |
|---|---|---|
| 실행 주체 | 모델 바깥, 결정론적 | 모델이 판단해서 호출 |
| 토큰 비용 | 0 | 도구 정의가 매 턴 컨텍스트 상주 |
| 누락 가능성 | 없음 | **모델이 안 부르면 그 턴은 소실** |

저장은 빠지면 안 되는 일이므로 모델 판단에 맡기지 않는다.
현행 요약이 이미 `claude -p --model claude-haiku-4-5-20251001` 로 **대화 바깥에서** 돈다
(`scripts/hermes-summarize.py:171-175`). 서버화의 추가 비용은 HTTP 왕복 하나뿐이다.

다른 창구(텔레그램 등)는 훅이 없지만, **봇 자체가 서버 안에 있으므로** 저장은 봇의 기본 동작이 된다.

### 3.3 무엇을 보내나 — 실측 기반

이 프로젝트 대화 로그(세션 10개, `.jsonl` 합계 **33.0MB**, 13,246줄)의 구성:

| 블록 | 크기 | 비중 | 서버 전송 |
|---|---|---|---|
| 도구 출력(`tool_result`) | 5.53 MB | 16.7% | ✗ |
| 첨부물 | 3.42 MB | 10.4% | ✗ |
| 내부 사고(`thinking`) | 2.55 MB | 7.7% | ✗ |
| 이미지 | 2.02 MB | 6.1% | ✗ |
| 도구 호출(`tool_use`) | 1.56 MB | 4.7% | ✗ |
| **사용자 발언** | **0.82 MB** | **2.5%** | **✓** |
| **어시스턴트 발언** | **0.38 MB** | **1.2%** | **✓** |

(합계가 100%에 못 미치는 것은 줄마다 붙는 JSON 메타데이터 때문이다.)

**진짜 대화는 1.2MB — 전체의 3.7%다.** 나머지는 재생성 가능하다.
파일 내용은 다시 읽으면 되고, 명령 결과는 다시 돌리면 된다.

내부 사고는 제외한다. 부피가 실제 대화의 두 배인데, 결정의 이유는 대개 답변 본문에 드러난다.

**규모 추산:** 프로젝트 20개 × 1.2MB ≈ 24MB, 텍스트 압축 시 6MB 남짓.
→ **용량은 제약이 아니다.** 제약처럼 보였던 것은 "무엇을 저장할지"를 안 정했기 때문이다.

**포기하는 것:** 도구 출력이 없으므로 다른 기기에서 `claude --resume` 수준의 세션 완전 재개는 안 된다.
대신 서버가 대화를 읽어 브리핑한다. 원래 목적("뭐 하다 말았나 / 왜 그렇게 정했나")에는 이쪽이 맞다.

### 3.4 키 설계

대화 한 줄(turn)의 구성:

| 칸 | 뜻 | 출처 |
|---|---|---|
| `user_id` | 나 — 창구가 뭐든 하나로 수렴 | 발급 (§4) |
| `source` | 창구 (`claude-code` / `telegram` / …) | 고정값 |
| `device_id` | 어느 기기 | 발급 (§4) |
| `project_id` | 무슨 맥락 | 매핑표 (§3.5) |
| `session_id` | 어느 대화 | Claude Code 가 이미 UUID 발급 |
| `seq` | 세션 내 순번 | `session_summary.last_msg_count` 가 이미 세고 있음 |
| `role` / `content` / `ts` | 누가 / 뭐라고 / 언제 | transcript |

**PK = `(session_id, seq)`.** 랜덤 ID 를 쓰지 않는다.

이유는 조회가 아니라 **재전송 멱등성**이다. 로컬 먼저 쓰고 미는 구조에서는 네트워크 복구 후
재전송이 반드시 발생한다. 랜덤 ID 면 같은 발언이 재시도 횟수만큼 중복 적재되고,
그 중복이 나중에 회상으로 되돌아온다. 자연키면 몇 번을 밀어도 한 줄이다.

앞의 네 칸(`user_id`/`source`/`device_id`/`project_id`)은 필터축이 된다 —
"이 프로젝트만", "텔레그램에서 한 것만", "이 기기에서 한 것만".

### 3.5 프로젝트 신원 — 경로가 아니라 매핑표

경로도 폴더명도 기기 간에 다를 수 있으므로 신원 근거로 쓸 수 없다.
신원을 프로젝트 안에서 찾지 말고 **기기마다 매핑표**를 둔다.

`~/.hermes/projects.map`: 이 기기의 로컬 경로 → 서버의 프로젝트 신원.

- **git 저장소:** 원격 주소를 정규화해 자동으로 채운다. 경로가 어디든 원격 주소는 같다.
- **비-git 폴더:** 새 기기에서 처음 세션을 열 때 한 번 묻고 표에 고정한다. 이후 재질문 없음.

부수 효과로 **동명이인 사고도 막힌다.** 우연히 같은 이름의 폴더가 있어도 신원이 다르면 섞이지 않는다.

### 3.6 읽기 — 세 단으로 나눈다

밀기와 대칭이 아니다. 밀 때는 전부 밀면 되지만 **당길 때는 컨텍스트 예산이 있다.**

| 단 | 언제 | 무엇을 | 비고 |
|---|---|---|---|
| 브리핑 | 세션 시작 1회 | `open` + `decisions` | 작으므로 무조건 주입. 현행 `--inject` 확장 |
| 관련분 검색 | 프롬프트마다 | 지금 주제와 관련된 과거 조각 | 현행 3계층 슬롯 예산에 서버 층 추가 |
| 파헤치기 | 사용자가 물었을 때만 | 원본 대화까지 | 자동 주입 금지 |

**검색은 서버가 수행한다.** 단순 저장소면 기기가 데이터를 통째로 받아 로컬에서 뒤져야 하고,
그러면 결국 파일 옮기기로 되돌아간다. 질의를 보내고 선별된 결과만 받는 구조여야
나중에 텔레그램 봇도 같은 것을 그대로 쓴다.

### 3.7 망각 — 잠은 한 군데서만 잔다

헤르메스에는 이미 망각 장치가 있다: `compaction_log`(압축 감사),
`state='demoted'`(미사용 스킬 강등), 드리밍(수면 중 통합).
**서버로 옮기면 두 가지가 어긋나므로 같이 옮겨야 한다.**

**① 실행자가 하나여야 한다.** 현행 드리밍은 SessionStart 에서 하루 1회 돈다.
기기가 셋이면 셋 다 자기 기준으로 돌려 같은 데이터를 중복 압축하거나 서로 덮어쓴다.
→ 기기는 밀어넣기만 하고, 통합·망각은 **서버가 정해진 시각에 단독 실행**한다.

**② 재사용 신호도 서버로 모아야 한다.** 낡음의 판단 근거인
`session_reuse` / `helpful_count` / `noop_count` / `last_helpful_at` 가 기기별로 갈라져 있으면,
A에서 반년째 안 쓴 지식이 B에서 매일 쓰이는 중일 수 있다.
**이대로 올리면 현역 지식을 잊는다.**
→ 어느 기기에서 꺼내 썼든 그 사실이 서버에 남아야 한다.
모이고 나면 오히려 지금보다 판단이 정확해진다. 지금은 한쪽 눈으로만 보고 있다.

### 3.8 보관 — 영구 저장, 선별 회상

1.2MB 규모이므로 원본 대화를 버릴 이유가 없다. **영구 보관한다.**

따라서 망각은 **삭제가 아니라 회상 대상에서 제외**하는 것으로 구현한다.
오래되고 안 쓰인 것은 브리핑에도 자동 검색에도 걸리지 않지만,
사용자가 단서를 주고 명시적으로 찾으면 나온다. 잘못 잊어 영구 소실될 위험이 없다.

## 4. 아직 정하지 않은 것

| # | 열린 질문 | 왜 걸리나 |
|---|---|---|
| 1 | **서버를 어디에 두나** | 여러 프로젝트의 대화 전부가 한곳에 모인다. 자가 호스팅 / 관리형 / 홈서버가 각각 인증·백업·보안을 다르게 만든다 |
| 2 | **채팅방의 세션 경계** | Claude Code 는 세션이 명확하지만 대화방은 끊김이 없다. 방 단위로 볼지, 무응답 간격으로 자를지 |
| 3 | **`user_id`·`device_id` 발급 방식** | 창구별 계정(텔레그램 등)을 하나의 `user_id` 로 묶는 표가 별도로 필요하다 |
| 4 | **원본 대화 마스킹 강도** | 현행 마스킹은 요약 경계에서 돈다. 원본을 서버로 보내면 관문이 더 촘촘해져야 한다 |
| 5 | **백업** | 뇌가 하나가 되면 그것이 유일본이다. 백업이 선택이 아니게 된다 |
| 6 | **다른 창구가 창구인가 입력원인가** | 텔레그램 봇으로 말을 거는 것(창구)과, 사람들끼리 나눈 대화를 수집하는 것(입력원)은 규모·성격이 전혀 다르다. 현재 논의는 **창구** 전제 |

## 5. 기존 자산과의 관계

새로 짓는 것이 아니라 기존 구조의 **바닥을 바꾸는** 작업이다.

| 기존 | 이 설계에서 |
|---|---|
| `hermes-summarize.py` | 유지. 결과를 로컬에 쓴 뒤 서버로 밀기 추가 |
| `hermes-recall.py --inject` | 유지. `--db` 가 서버도 보게 확장 |
| `hermes-search.py` 3계층 | 유지. 서버 층 추가, 슬롯 예산 재배분 |
| `~/.hermes/mesh/skills/` | 유지. 일반화된 지식 층은 이미 목적을 달성 중 |
| 드리밍 (SessionStart) | **서버 단독 실행으로 이전** |
| `project_id = basename` | **매핑표로 교체** |
| `.gitignore` 의 `.hermes/` | 유지. 로컬 캐시 성격은 변하지 않는다 |
