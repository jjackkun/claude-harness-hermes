# R-cov — 커버리지 강제

> 작성일: 2026-08-24
> 목적: 문서 7곳이 약속한 "80% 커버리지"를 문장이 아니라 게이트로 만든다.

## 개요

하네스 자산 7개 파일이 커버리지 임계를 명시한다 —
`tdd-workflow/SKILL.md`("최소 80%"), `tdd-guide.md`("80%+ 보장"),
`springboot-tdd/SKILL.md`, `rules/java/testing.md`, `rules/dart/testing.md`,
`rules/web/testing.md`, `verification-loop/SKILL.md`.

**그런데 이를 검사하는 게이트가 없다.** `pre-commit` 의 `R-test` 는 pytest 의
성공/실패만 본다. 커버리지는 측정조차 하지 않는다.

영상이 지적한 실패 모드가 그대로다 — 자연어로 적힌 규율은 가이드라인으로 취급된다.
그리고 CRAP 스코어는 `복잡도 x 커버리지` 인데, 우리는 지금 **양쪽 다 미측정**이다.
(복잡도 축은 `2026-08-24-complexity-gate-design.md` 가 다룬다.)

## 문제 — R-test 는 사실상 no-op 이다

측정하기 전에 더 근본적인 문제가 나왔다.

### 1. 파이썬 단위 테스트가 0개다

`tests/` 의 28개 파일이 **전부 bash 통합 테스트**다(`*-test.sh`).
`git ls-files '*test*.py'` 로 잡히는 파일은 `assets/` 아래의 규칙 예시 문서와
외부에서 들여온 스킬 스크립트뿐이며, 이 저장소 운영 코드의 단위 테스트가 아니다.

### 2. 그래서 R-test 는 항상 통과한다

`pre-commit.sh:159` 의 처리:

```bash
# 종료코드 캡처. exit 0=통과, 5=수집 0개 → 통과로 간주. 그 외(실패/중단/에러)는 차단.
if [[ "$PYTEST_RC" -ne 0 && "$PYTEST_RC" -ne 5 ]]; then
```

`pytest tests/` 는 수집 0개로 **항상 exit 5** 를 낸다. 그리고 5는 통과로 간주된다.
**이 저장소에서 `R-test` 단계는 한 번도 무언가를 막은 적이 없다.**

exit 5 를 통과로 두는 판단 자체는 옳다 — 파이썬이 없는 프로젝트에도 설치되는 훅이므로.
문제는 이 저장소가 그 예외 경로에 영구히 머물러 있다는 사실을 아무도 모른다는 점이다.

**커버리지 임계를 걸기 전에 잴 대상부터 만들어야 한다.**

## 설계 — 2단계

### 1단계: 침묵 해소 — **완료 (2026-08-24)**

커버리지보다 먼저 **"테스트가 없다"는 사실이 보이게** 만든다.

`R-test` 가 exit 5 를 만났을 때 조용히 통과하는 대신 `WARNINGS` 에 기록한다.
차단은 하지 않는다 — 파이썬 없는 프로젝트를 막으면 안 된다.

```text
[R-test] 스테이징된 .py 가 있으나 수집된 테스트가 0개다.
  이 커밋의 파이썬 변경은 어떤 테스트로도 검증되지 않는다.
  근거: docs/design-docs/core-beliefs.md#r-test
```

**발화 조건은 "스테이징에 `.py` 가 있는데 테스트가 0개"** 다.
파이썬을 안 쓰는 프로젝트는 `PY_FILES` 가 비어 이 단계에 들어오지 않는다.

**구현 중 상태가 하나 더 늘었다 — pytest 실행 불가.**
초안은 "실패 / 수집 0개" 둘만 봤으나, 구현 중 세 번째 상태가 드러났다:
pytest 실행 파일은 PATH 에 있는데 자기 모듈을 import 하지 못하는 경우다.
예전 코드는 이를 `[R-test] pytest 실패` + Traceback 으로 보고하며 **커밋을 막았다** —
도구가 못 뜬 것을 테스트 실패로 보고하면 사람이 자기 코드를 뒤지게 된다.
`pytest --version` 선행 확인으로 구분하고 경고로 낮춘다.

실측 경로: `HOME` 이 바뀌면 user-site(`~/.local/lib/.../site-packages`)가 사라져
실행 파일은 남고 import 만 깨진다. `tests/harness-hooks-smoke.sh` 가 `HOME` 을
격리하는 순간 이 증상이 그대로 재현됐다.

`WARNINGS` 배열은 이미 존재한다(`pre-commit.sh:74`) — 차단하지 않는 경고를
`VIOLATIONS` 와 분리해 출력하는 기존 장치를 그대로 쓴다.

### 2단계: 커버리지 임계 (1단계 이후)

측정 가능한 테스트가 생긴 뒤에만 의미가 있다.

| 항목 | 값 |
|---|---|
| 도구 | `assets/hooks/coverage_probe.py` — 표준 라이브러리 `trace` 기반 자체 구현 |
| 대상 | 스테이징된 `.py` 의 **변경 라인** |
| 임계 | 미확정 — 아래 참조 |
| 행동 | 경고 → (관측 후) 차단 |

**전체 커버리지가 아니라 변경 라인 커버리지(diff coverage)를 쓴다.**
전체 임계는 레거시가 많은 저장소에서 첫날부터 실패하고, 그러면 즉시 꺼진다.
변경 라인 기준은 "새로 쓰는 코드는 테스트한다"만 요구하므로 도입이 가능하다.

**임계 80% 를 그대로 쓰지 않는다.** 문서 7곳의 80% 는 출처가 불명확한 관습값이다.
1단계로 테스트가 쌓인 뒤 실제 분포를 재서 산정한다.
그때까지 이 스펙은 임계를 확정하지 않는다.

### bash 통합 테스트의 커버리지 측정

이 저장소의 테스트는 파이썬 스크립트를 subprocess 로 호출하는 bash 다.
`coverage run` 은 subprocess 를 기본으로 추적하지 않으므로 그대로는 0% 가 나온다.

`PYTHONPATH` 에 `sitecustomize.py` 를 두면 인터프리터가 뜰 때마다 추적이 자동으로 붙는다.
표준 라이브러리만 쓰며, `coverage.py` 의 `COVERAGE_PROCESS_START` 와 같은 수법이다.
2026-08-25 실측으로 동작을 확인했다 — bash 가 띄운 하위 파이썬의 미실행 줄이 그대로 잡힌다.

## 미해결

1. **이 저장소의 파이썬 단위 테스트를 실제로 쓸 것인가.**
   1단계는 부재를 드러낼 뿐 해결하지 않는다. 28개 bash 통합 테스트가 있는 상태에서
   단위 테스트를 따로 쌓는 것이 맞는지, 아니면 bash 테스트의 커버리지를 측정하는 쪽이
   맞는지 결정이 필요하다. 후자가 비용이 낮다.
2. ~~**`coverage.py` 설치 요구가 하네스 배포에 미치는 영향.**~~ — **해소됨(2026-08-25).**
   "커버리지는 자체 구현이 현실적이지 않다" 는 검증 없이 적은 전제였고 틀렸다.
   표준 라이브러리 `trace` 로 하위 프로세스까지 측정된다(실측 확인). 외부 의존을 0건으로
   되돌렸으므로 미설치 처리 자체가 불필요해졌다. 상세는 로드맵 "외부 도구 방침" 절.
