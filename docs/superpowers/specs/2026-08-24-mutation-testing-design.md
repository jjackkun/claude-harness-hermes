# R-mut — 변이 테스트

> 작성일: 2026-08-24
> 목적: 테스트의 **존재**가 아니라 **유효성**을 검증한다. 회귀를 실제로 잡는지 확인한다.

## 개요

`tests/` 에 28개 테스트가 있고 `R-test` 가 이를 돌린다. 그러나 **그 테스트들이 실제로
회귀를 잡는지는 검증된 적이 없다.** 통과하는 테스트와 유효한 테스트는 다르다.

변이 테스트는 소스의 연산자·경계를 강제로 뒤집고(`>` ↔ `<`, `==` ↔ `!=`, `and` ↔ `or`),
기존 테스트가 그 변이를 잡아내 실패하는지 본다. 잡으면 killed, 통과하면 survived —
생존한 변이는 **그 코드 경로를 검증하는 테스트가 없다**는 뜻이다.

## 실측 — 파일럿 (2026-08-24)

원본을 백업하고 변이를 주입한 뒤 해당 테스트를 실행, 원본 복원까지 수행했다.

### 대상과 결과

| 모듈 | 테스트 | 변이 | 잡힘 | 변이 점수 |
|---|---|---|---|---|
| `scripts/hermes_mesh_gate.py` | `hermes-mesh-gate-test.sh` | 5 | 4 | **80%** |
| `assets/hooks/plan_state.py` | `plan-state-test.sh` | 8 | 8 | **100%** |
| 합계 | | 13 | 12 | 92% |

**기존 테스트의 품질은 예상보다 높다.** 착수 전 가설("bash 테스트는 껍데기일 것")은 틀렸다.

### 생존 변이 1건 — 실제 검증 공백

```text
scripts/hermes_mesh_gate.py:80   or → and   ★생존★
  prompt = _PROMPT_TMPL.format(body=(text or "")[:_MAX_PROMPT])
```

`text or ""` 를 `text and ""` 로 바꾸면 `text` 가 truthy 일 때 body 가 **빈 문자열**이 된다.
프롬프트 본문이 통째로 사라지는데 테스트는 통과한다.
`hermes-mesh-gate-test.sh` 가 **프롬프트 본문의 내용을 단언하지 않는다**는 뜻이다.

이것이 변이 테스트가 찾아내는 종류의 공백이다. 커버리지로는 안 보인다 —
그 라인은 실행되므로 커버리지 100% 로 잡힌다.

### 비용

테스트 실행 시간 실측: `hermes-redact-test.sh` 25ms, `plan-state-test.sh` 507ms,
`hermes-mesh-gate-test.sh` 1,315ms.

파일럿 13개 변이의 총 비용은 약 11초였다. **모듈 단위로는 충분히 저렴하다.**

## 설계

### 도구 — 자체 구현

`mutmut` 은 미설치이며, 설치해도 **이 저장소에는 그대로 쓸 수 없다.**
`mutmut` 은 테스트 러너로 pytest 를 가정하는데, 이 저장소의 테스트는 bash 다
(28개 중 23개가 `python3 "$S/hermes-*.py"` 형태로 파이썬을 실행한다).

파일럿에서 쓴 방식을 스크립트로 정착시킨다: **변이 주입 → 지정 테스트 실행 → 원본 복원.**
표준 라이브러리만 쓰므로 설치 요구가 없다 — `R-cx` 에서 `radon` 을 피한 것과 같은 판단이다.

`scripts/mutation-probe.py` 로 만든다.

```bash
python3 scripts/mutation-probe.py --target scripts/hermes_loop.py --test tests/hermes-loop-test.sh
```

**원본 복원은 실패 경로에서도 보장되어야 한다.** 파일럿은 정상 종료 시에만 복원했다.
`try/finally` + 시작 시 백업 + 종료 시 `diff` 검증을 구현 요건에 포함한다.

### 변이 규칙

| 원본 | 변이 |
|---|---|
| `>=` | `<` |
| `<=` | `>` |
| `==` | `!=` |
| `!=` | `==` |
| ` and ` | ` or ` |
| ` or ` | ` and ` |
| ` not ` | (삭제) |

주석 라인과 문자열 리터럴 시작 라인은 제외한다. 라인당 최대 1개 변이.

### 발화 — 게이트가 아니다

**`pre-commit` 에 넣지 않는다.** 두 가지 이유다.

1. 비용이 커밋 경로에 맞지 않는다. 모듈 하나는 10초지만 전체는 수 분 단위다.
2. 변이 점수의 임계값을 정할 근거가 아직 없다. 표본이 2개 모듈, 13개 변이뿐이다.

대신 **주기적 진단**으로 운영한다.

| 항목 | 값 |
|---|---|
| 실행 | 수동 (`scripts/mutation-probe.py`) + 향후 cron 후보 |
| 출력 | 생존 변이 목록 → `docs/audits/YYYY-MM-DD-mutation-*.md` |
| 행동 | 차단 없음. 생존 변이가 곧 "테스트를 추가할 지점" 목록 |

영상의 Hardener 역할이 이것이다 — 변이 테스트로 테스트 누락을 보강한다.
다만 영상은 에이전트 파이프라인 안에 두고, 우리는 먼저 진단 도구로 세운다.
파이프라인 편입은 `2026-08-24-agent-pipeline-enforcement-design.md` 가 다룬다.

## 검증

| 항목 | 방법 |
|---|---|
| 복원 보장 | 테스트가 timeout/크래시로 죽어도 원본이 복원되는지 |
| 복원 검증 | 실행 후 `git diff --exit-code <target>` 가 깨끗한지 |
| 재현성 | 파일럿 결과(mesh_gate 4/5, plan_state 8/8) 재현 |
| 동등 변이 | 의미가 바뀌지 않는 변이를 생존으로 오보고하지 않는지 |

`tests/mutation-probe-test.sh` 를 추가한다 — **복원 보장이 핵심 테스트다.**
소스를 망가뜨린 채 종료하는 도구는 도구가 아니라 사고다.

## 미해결

1. **동등 변이(equivalent mutant) 처리.** 의미가 바뀌지 않는 변이는 원리적으로 잡을 수 없고,
   생존으로 보고되면 노이즈가 된다. 파일럿 표본이 작아 발생률을 모른다.
   전체 실행 후 실제 비율을 보고 판단한다.
2. **모듈 ↔ 테스트 매핑.** 현재 수동 지정이다. `hermes_loop.py` 를 검증하는 테스트가
   `hermes-loop-test.sh` 하나인지 여러 개인지 자동으로 알 방법이 없다.
   naming convention 기반 추정 + 수동 override 가 현실적이다.
3. **변이 점수 임계.** 표본이 부족하다. 전체 모듈 1회 실행 후 분포를 보고 산정한다.
