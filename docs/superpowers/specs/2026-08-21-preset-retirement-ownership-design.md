# 프리셋 은퇴 축 — 지운 것이 배포처에 남는다

> 작성일: 2026-08-21
> 목적: 프리셋을 저장소에서 지워도 이미 설치된 프로젝트에서는 걷어지지 않고,
> 오히려 **업데이트 자체를 막는** 두 결함을 없앤다.
> 계기: `ee86a0a`(세레나 제거) 이후 11개 중 6개 프로젝트가 재설치 불가 상태였음 — §1-1

## 1. 동기 (Why)

### 1-1. 실제로 일어난 일

```
8/21  ee86a0a   presets/workflow/serena.conf 삭제
                lib/uninstall_helpers.sh 의 회수 함수도 같은 커밋에서 삭제
      (그 사이) 아무도 update-all.sh 를 돌리지 않아 아무도 몰랐다
8/21  update-all → 11곳 중 6곳 실패
                  Unknown preset: 'serena'
```

여섯 프로젝트는 **세레나만 못 받은 것이 아니라 그 뒤의 모든 하네스 업데이트를 못 받고
있었다.** 오늘 R-size 책임 신호를 전파하려다 드러났다. 프리셋 하나를 지운 대가가
"그 프리셋이 안 깔린다" 가 아니라 **"업데이트 파이프가 통째로 막힌다"** 였다.

### 1-2. 하네스는 이 함정을 이미 알고 있었다

`lib/hook_inventory.sh:12` 는 이렇게 적혀 있다.

> 소유 판별은 `assets/hooks/` 디렉터리 스캔에 의존하므로, 파일을 지우는 순간
> **"하네스 소유"로 인식되지 않아 기존 프로젝트에서 제거할 수 없게 된다.**
> 배포 중단한 hook 은 파일을 지우기 전에 반드시 여기 등재한다.

★ **hook 에는 이 방비가 있고 preset·permission 에는 없다.** 세레나는 방비가 없는
쪽으로 나갔다. `serena.conf` 는 `HARNESS_PERMISSIONS_ALLOW+=(...)` 로 권한 28건을
직접 넣었는데, 파일이 사라지자 **그 28건이 하네스 것이라는 증거도 함께 사라졌다.**

### 1-3. 두 번째 결함 — 권한은 애초에 회수되지 않는다

`lib/generate_settings_json.py:16` 이 정책을 명시한다.

> `permissions.allow` is merge-only — nothing is deleted when a preset stops
> providing a value.

`hooks` 는 소유권 동기화가 되고 `permissions.deny` 의 `Agent(...)` 는 프리셋 관리
네임스페이스인데, **`allow` 만 한 번 들어가면 영구히 남는다.** 오늘 6개 프로젝트에서
지운 죽은 권한 184건이 그 결과다.

```
hooks                 소유권 동기화 ✓   프리셋에서 빠지면 걷힌다
permissions.deny      Agent() 만 동기화 ✓
permissions.allow     ✗ 영구 누적
presets.lock          ✗ 유령 항목이 파이프를 막는다
```

## 2. 문제 정의

```
① lock 유령 항목이 차단이 된다   기계가 쓴 lock 의 한 줄 때문에 재설치 전체가 실패
② allow 가 회수되지 않는다        프리셋이 빠져도 권한은 남는다
③ 은퇴 등재처가 hook 에만 있다    preset·permission 은 지우면 소유 증거가 사라진다
```

## 3. 설계 결정

### 3.0 지배 원칙

```
기존 패턴을 따른다        hook 의 소유권 동기화가 이미 정답이다. 새 개념을 만들지 않는다
사용자 것은 건드리지 않는다  하네스가 넣은 적 없는 항목은 영구 보존
오타는 계속 막는다         CLI 인자의 오타 보호를 잃으면 안 된다
차단을 늘리지 않는다        유령 항목은 경고 후 진행. 막는 것이 오늘의 문제였다
```

### 3.1 lock 유령 항목 — 경고 후 진행 (①)

**핵심 구분: `presets.lock` 은 기계가 쓴 파일이고 CLI 인자는 사람이 친 것이다.**

```
CLI 인자        오타일 수 있다        → 지금처럼 즉시 실패 (변경 없음)
presets.lock    과거 설치의 기록      → 유효하지 않다면 하네스가 그 프리셋을
                                       버렸다는 뜻. 경고 후 빼고 진행
```

lock 에 유효하지 않은 항목이 있다는 것은 **정의상** 예전에 존재했다가 사라진
프리셋이다. 사람이 lock 을 손으로 쓰지 않는다. 그러므로 은퇴 목록 대조가 필요 없다 —
유효성 검사 하나로 충분하다.

- 대상: `update-all.sh` 의 lock 읽는 자리
- 동작: 유효하지 않은 항목을 경고와 함께 제외하고, 정리된 lock 을 다시 쓴다
- 판정: `serena` 가 든 lock 으로도 재설치가 성공하고, lock 에서 `serena` 가 사라진다

### 3.2 allow 소유권 동기화 (②)

`hooks` 와 **같은 방식**을 쓴다.

```
하네스 소유 allow 항목 =  모든 preset .conf 가 제공하는 항목의 합집합
                        ∪ assets/permissions/*.json 의 항목
                        ∪ RETIRED_PERMISSION_ALLOW (은퇴 등재분)
```

매 실행마다 **하네스 소유 항목을 기존 allow 에서 걷어내고**, 지금 선택된 프리셋이
제공하는 것만 다시 넣는다. 그 밖의 항목은 사용자 것이므로 손대지 않는다.

- 대상: 새 `lib/permission_inventory.sh` (단일 책임: 소유 목록 제공) ·
  `lib/settings_gen.sh` (목록 전달) · `lib/generate_settings_json.py` (회수 후 병합)
- 판정: 프리셋을 빼면 그 권한이 사라진다 / 사용자가 손으로 넣은 항목은 남는다

⚠️ **감수하는 것.** 사용자가 손으로 넣은 항목이 하네스 항목과 **문자열까지 같으면**
회수 대상이 된다. `hooks` 가 이미 같은 트레이드오프를 지고 있고, 이것 없이는
소유 판별이 불가능하다. 대안(주입 시점 표식 기록)은 settings.json 스키마를 바꿔야 해서
비용이 크다.

### 3.3 은퇴 등재처 (③)

`RETIRED_HOOK_SOURCES` 와 같은 자리에 `RETIRED_PERMISSION_ALLOW` 를 둔다.
**세레나의 28건을 초기값으로 넣는다** — 오늘 등록된 11곳은 수동 정리했지만
레지스트리 밖의 설치본은 남아 있을 수 있고, 무엇보다 **이 장치가 실제로 도는지
확인할 표본**이 된다.

### 3.4 프리셋 삭제 절차를 문서에 박는다

장치만으로는 다음 사람이 또 순서를 틀린다. `ee86a0a` 는 회수 함수를 **회수가
실행되기 전에** 지웠다.

```
프리셋을 배포 중단할 때
  1. RETIRED_PERMISSION_ALLOW 에 그 프리셋의 allow 항목을 등재
  2. RETIRED_HOOK_SOURCES 에 그 프리셋의 hook 파일명을 등재
  3. update-all.sh 를 돌려 설치본에서 회수가 끝난 것을 확인
  4. 그 다음에 .conf 와 회수 코드를 지운다
```

## 4. 위험

| 위험 | 징후 | 대응 |
|---|---|---|
| **사용자 권한 오회수** | 손으로 넣은 항목이 사라짐 | §3.2 ⚠️ — hook 과 동일 트레이드오프. 문자열 완전 일치일 때만 |
| **lock 조용한 축소** | 의도한 프리셋이 말없이 빠짐 | 경고를 반드시 출력. 조용히 빼지 않는다 |
| **은퇴 등재를 또 빠뜨림** | 다음 프리셋 제거 때 재발 | §3.4 절차 + 등재처가 한곳 |
| **전 프리셋 소싱 비용** | 설치가 느려짐 | 27개 파일 subshell 소싱. 측정해서 확인 |

## 5. 발견

- ★ **막힌 것을 아무도 몰랐다.** `update-all.sh` 는 실패를 정직하게 출력했지만
  **아무도 돌리지 않으면 출력은 존재하지 않는다.** 오늘 다른 일로 돌리지 않았다면
  여섯 프로젝트는 계속 조용히 뒤처졌을 것이다.
- ⚠️ **주석이 함정을 정확히 경고하고 있었는데도 밟았다.** `hook_inventory.sh:12` 는
  이 사고를 문장으로 예언한다. **장치가 없는 곳에 경고문만 있으면 밟힌다** —
  §3.3 이 등재처를, §3.4 가 절차를 두는 이유다.
