# 인터페이스 폭 게이트 — 분리 시점을 500줄에서 파일 탄생으로 옮긴다

> 작성일: 2026-08-24
> 목적: 책임 분리 판단을 "줄 수 한도에 도달했을 때"가 아니라 "파일이 태어날 때" 일어나게 한다.

## 개요

현재 하네스에서 **책임 분리를 강제하는 유일한 지점은 `R-size` 의 500줄 한도**다.
그 결과 분리는 (1) 늦게, (2) 기계적으로 일어난다. 500줄까지 자란 파일을 사후에 가르면
책임 경계가 아니라 줄 수 경계로 잘리고, 숨어 있던 내부 함수가 파일 밖으로 나오며
**공개 심볼로 승격**된다. 인터페이스가 넓어진다 — 모듈을 깊게 만들라는 원칙의 반대다.

본 스펙은 500줄 한도를 건드리지 않는다. 대신 **그 앞 단계 세 곳**에 신호를 놓아,
500줄에 도달하기 전에 구조 판단이 끝나게 한다.

## 문제 — 실측

### 줄 수 게이트가 반대로 압력을 준다

`scripts/*.py` 실측(2026-08-24):

| 파일 | 줄 수 | 공개 | 비공개 | 은닉률 |
|---|---|---|---|---|
| `hermes-lifecycle.py` | 483 | 7 | 14 | 66% |
| `hermes_loop.py` | 385 | 19 | 1 | 5% |

- `hermes-lifecycle.py` 는 공개 7개 뒤에 비공개 14개를 감춘 **은닉률 66% 의 깊은 모듈**이다.
  그런데 500 한도까지
  17줄 남아 가장 먼저 차단된다. 쪼개면 비공개 14개 중 일부가 경계를 넘으며 공개로 승격돼
  **더 얕아진다.**
- `hermes_loop.py` 는 사실상 모든 내부가 노출돼 있으나, 115줄 여유라 **아무 신호도 받지 않는다.**

게이트가 잘 설계된 파일을 먼저 때리고 못 설계된 파일을 방치한다.

### `hermes_loop.py` 는 실제로 책임이 5개다

공개 심볼 19개를 분류한 결과:

| 책임 | 심볼 |
|---|---|
| DB 연결·스키마 | `connect_db`, `ensure_schema` |
| goal.md 입출력 | `goal_md_path`, `read_goal_md`, `append_progress_log`, `update_goal_status` |
| 루프 레코드 CRUD | `create_loop`, `get_loop`, `list_loops`, `record_iteration`, `finish_loop`, `archive_loop` |
| 정책 판정 | `default_max_iterations`, `check_caps`, `checked_count` |
| 외부 실행 | `run_verify`, `git_head`, `ensure_loop_branch` |

파일명 `loop` 가 약속한 책임은 하나인데 다섯이 들어 있다.
`update_goal_status`·`default_max_iterations` 는 **외부 사용처 0건인데 공개**다.

### 신규 파일은 현재 완전한 사각지대

`claude-posttooluse-size-warn.sh` 의 책임 델타 신호는 신규 파일을 명시적으로 건너뛴다:

```bash
# HEAD 에 없는 파일(신규)은 건너뛴다: 기준선이 없으면 "증가" 를 말할 수 없고
REL=$(git ls-files --full-name --error-unmatch -- "$FILE_PATH" 2>/dev/null) || exit 0
```

기준선이 없으므로 델타를 못 쓴다는 판단 자체는 옳다. 그러나 그 결과
**새 파일은 400줄에 도달할 때까지 어떤 신호도 받지 않는다** — 구조를 정해야 할 바로 그 순간에.

## 설계 — 세 축

세 축은 파일 생애의 서로 다른 시점을 덮는다. 하나만 넣으면 나머지 둘로 샌다.

| 축 | 시점 | 현재 상태 |
|---|---|---|
| A. `R-iface` | 파일을 **만들기 전** | 없음 (신설) |
| B. 델타 신호 오탐 제거 | 파일이 자랄 때 | 있으나 공개/비공개 미구분 |
| C. 배럴 폭 검사 | 나눈 뒤 | 존재 여부만 검사 |

---

### 축 A — `R-iface`: 파일 생성 전 인터페이스 폭

**발화 지점**: `PreToolUse(Write)`. Write 가 **실행되기 전**에 끼어든다.

`PostToolUse` 가 아닌 이유가 이 축의 핵심이다. PostToolUse 는 파일이 이미 쓰인 뒤에
실행되므로, 300줄짜리 파일을 다 써놓고 "나눌래?" 라고 묻게 된다. 500줄보다 앞당겼을 뿐
여전히 사후 대응이고, 원칙("구조를 먼저 잡는다")과 어긋난다.

PreToolUse 는 `tool_input.content` 에 **쓰려는 내용**을 담고 있으므로,
파일이 생기기 전에 공개 심볼을 셀 수 있다.

**대상**: `tool_input.file_path` 가 **아직 존재하지 않는** 경우만.
이미 있는 파일에 대한 Write 는 덮어쓰기이며 축 B 관할이다.
PreToolUse 시점에는 파일이 아직 안 만들어졌으므로 이 판정이 자명하다 —
PostToolUse 안이 안고 있던 "신규 파일을 어떻게 아는가" 문제가 사라진다.

**판정**: `tool_input.content` 의 공개 심볼 수 >= 8.

**구현은 AST 로 한다.** 정규식(`^def `)은 삼중따옴표 문자열 안의 `def` 를 오탐하고,
데코레이터·조건부 정의의 취급이 모호하다. `ast.parse(content)` 후 모듈 최상위의
`FunctionDef`/`AsyncFunctionDef`/`ClassDef` 중 이름이 밑줄로 시작하지 않는 것을 센다.

`content` 가 아직 문법적으로 온전하지 않아 파싱이 실패하면 **통과시킨다** —
문법 오류는 다른 게이트의 관할이고, 파싱 실패로 파일 생성을 막으면
정상 작업이 원인 불명으로 차단된다.

(같은 이유로 `R-cx`·`R-dep` 도 AST 로 구현한다.
초안의 `R-dep` 은 정규식을 써서 들여쓴 import 9개를 놓쳤다 —
`2026-08-24-ai-engineering-gap-roadmap.md` 의 "측정 방법" 절 참조.)

공개 심볼의 정의(아래 패턴은 의미를 설명하는 것이고, 구현은 AST 다):

| 확장자 | 패턴 | 제외 |
|---|---|---|
| `.py` | `^(def \|class \|async def )[a-zA-Z]` | `def main(` — CLI 진입점이지 인터페이스가 아니다 |
| `.js` `.jsx` `.ts` `.tsx` | `^export ` | — |
| `.svelte` | 미해결 — 아래 참조 | — |

**임계 8 의 근거**: 저장소 운영 코드 36개 파일의 공개 심볼 수 분포는

```text
19, 15, 13, 11, 10, 9, 8, 7, 7, 7, 7, 6, 6, 5, 4, 4, 3, 3, 3, 3, 3, 3, 3, 3, 2, 2, ...
```

**7 이 최빈 고원**(4개가 뭉쳐 있음)이고 8 부터가 상위 사분위다.
고원 안을 자르지 않고 고원 바로 위에서 자른다.

**행동**: 차단한다.

**차단 근거 — 시점이 바뀌면 오탐 비용이 바뀐다.**
분포에 판별력 있는 간극이 없다는 사실(19→15→13→11→10→9→8 이 연속)은 그대로다.
간극 없는 지표로 **커밋을 막으면** 안 된다 — 그 시점에는 작업이 이미 끝나 있어
오탐 하나가 완성된 코드의 재구성을 요구하고, 그래서 우회가 상시화된다.

그러나 `PreToolUse` 에서는 **아직 아무것도 쓰이지 않았다.** 오탐 비용은 거의 0 이다.
에이전트는 구조를 다시 잡거나, 한 책임임을 밝히고 다시 시도하면 된다.
같은 지표라도 차단 시점에 따라 성립 여부가 갈린다.

**차단 메시지**:

```text
[R-iface] scripts/foo.py 생성 차단 — 공개 심볼 8개.
  파일을 만들기 전에 답할 것: 이 8개가 지는 책임은 몇 개인가?
  2개 이상이면 폴더+배럴 구조를 먼저 만들고 각 파일에 나눠 쓸 것.
  1개라면 그 근거를 파일 상단 주석에 남기고 다시 시도할 것.
  근거: docs/design-docs/core-beliefs.md#r-iface
```

**예상 마찰**: 저장소 기존 파일 36개 중 7개(19%)가 임계 8 을 넘는다.
그러나 축 A 는 **새로 만드는 파일의 첫 Write** 에만 발화하므로 실제 빈도는 이보다 낮다.
차단 게이트에서는 발화 빈도가 곧 마찰이므로, 설치 후 실제 발화율을 관측해
임계 8 이 과발화하면 재산정한다. 과발화한 차단은 우회를 학습시킨다.

**우회 경로**: 파일 상단 주석에 근거를 남기면 통과한다.
`R-size` 의 waiver 와 같은 구조이며, 우회 자체를 막는 것이 목적이 아니라
**우회하려면 이유를 적게 만드는 것**이 목적이다.

### 축 A 의 강제 모델 — 기존 관행에서 벗어난다

이 저장소의 기존 `PreToolUse` 훅 두 개(`agent-guard`, `bash-guard`)는
**의도적으로 차단하지 않는다.** `agent-guard` 헤더에 그 결정이 기록돼 있다:

```text
강제 모델: 다른 hook 과 동일하게 soft warning. 차단이 아니라 컨텍스트 주입으로
에이전트가 자기 검열하도록 유도. 강한 차단을 원하면 stdout 에 decision: block 추가
가능하나 (Claude Code 일부 버전에서 지원), 호환성 위해 컨텍스트 주입 방식 채택.
```

`R-iface` 는 이 관행에서 벗어나 **저장소 최초의 하드 차단 PreToolUse 훅**이 된다.
근거는 위 "차단 근거" 절이다 — 경고는 무시될 수 있고, 무시되면 이 축은 존재 이유가 없다.
구조를 먼저 잡게 만드는 것이 목적이므로 통과 가능한 신호로는 목적을 달성하지 못한다.

**호환성 처리 (2단 강등)**:

1. `hookSpecificOutput.permissionDecision: "deny"` 로 차단을 시도한다.
2. 그 필드가 무시되는 버전에서는 `additionalContext` 주입으로 자동 강등된다 —
   기존 훅들과 같은 soft 모델이 된다. 훅이 조용히 죽지는 않는다.

두 경로 모두 같은 메시지를 낸다. 구현 시 실제 동작 버전을 확인해 기록한다.

### 축 B — 델타 신호의 오탐 제거

**현재 결함**: `claude-posttooluse-size-warn.sh` 의 Python 심볼 패턴이 공개와 비공개를 구분하지 않는다.

```bash
*.py) SYM_PAT='^(def |class |async def )' ; SYM_UNIT='최상위 def/class' ;;
```

비공개 헬퍼 5개를 추가하는 편집 — 즉 내부를 깊게 만드는 **개선** 편집 — 이
"책임이 +5 늘었다"는 경고를 받는다. JS 쪽 `^export ` 는 이미 공개만 세므로 Python 만 어긋나 있다.

**수정**: 임계값 5 는 그대로 두고, **발화 조건에 "공개 심볼도 늘었는가"를 AND 로 추가**한다.

```bash
# 전체 델타 >= 5  AND  공개 델타 > 0  일 때만 발화
(( SYM_NOW - SYM_BASE >= RESP_DELTA_WARN )) && (( PUB_NOW - PUB_BASE > 0 ))
```

**임계 5 를 유지하는 이유**: 5 는 마크다운·코드 양쪽 실측에서 나온 값이고
근거 문서(`2026-08-21-responsibility-over-linecount-design.md`)가 살아 있다.
이번 변경은 임계값 재산정이 아니라 오탐 제거다.

**공개 심볼 델타를 독립 임계로 쓰지 않는 이유** — 실측 결과 판별력이 없다.
최근 300커밋에서 기존 `.py` 파일의 공개 심볼 증가 이벤트는 11건, 최대 +4다:

```text
+4  scripts/hermes_lifecycle_apply.py   fix(hermes): 압축 데이터손실 차단(DB행수 가드)…
+4  scripts/hermes-recall.py            fix(hermes-recall): 회상 검색이 대화 원문을 뒤진다
+2  scripts/hermes-lifecycle.py         feat(hermes): 생애주기 압축 제안…
+2  scripts/hermes-search.py            feat(hermes): 훅 전용 플래그 3개
+1  × 7건
```

관측된 최대치 +4 가 **전부 정상적인 기능 추가**였다.
임계를 3~4 로 내리면 이 커밋들이 오탐으로 걸리고, 5 로 두면 발화가 0 이다.
어느 쪽도 성립하지 않으므로 독립 축으로 만들지 않는다.

### 축 C — 배럴 폭 검사

**현재 결함**: `assets/hooks/check-component-structure.mjs` 의 `R-struct-2` 는
배럴의 **존재 여부만** 검사한다. 무엇을 내보내는지는 보지 않는다.

전량 재export 하는 배럴은 아무것도 감추지 않는다. import 경로만 짧아질 뿐,
호출자가 알아야 할 심볼 수는 그대로다 — 축 A 가 "나눠라"라고 해서 나눈 결과가
이 형태면 인터페이스 폭은 하나도 줄지 않는다.

```javascript
// 감춤 아님 — 하위 파일의 모든 공개 심볼이 그대로 노출된다
export * from './parse.js'

// 감춤 — 선별해서 내보낸다
export { parse } from './parse.js'
```

**신설 규칙 `R-struct-4`**: 배럴 파일(`index.js` / `index.ts` / `__init__.py`)에서
전량 재export 구문을 금지한다.

| 언어 | 금지 패턴 |
|---|---|
| JS/TS | `export * from` |
| Python | `from .<module> import *` |

**임계값이 필요 없다.** "전량 재export 인가"는 이분 판정이다.
축 A 가 차단하지 못하는 것과 달리, 이 규칙은 간극 문제가 없으므로 **차단 가능**하다.

**적용 위치**: `check-component-structure.mjs` 에 추가하여 `R-struct` 단계에서 함께 검사.
현재 `R-struct` 는 Vue 프로젝트 대상이므로, 대상 확장 여부는 구현 시 결정한다.

## 500줄 한도의 처리

**변경하지 않는다.** 세 축이 상류에서 작동하면 500줄까지 도달하는 일 자체가 줄어든다.

`core-beliefs.md#r-size` 의 서술("500은 안전망")은 그대로 유효하다.
안전망을 제거하는 것은 상류 신호가 실제로 작동하는지 확인한 뒤에 판단할 별개 사안이다.

## 문서 변경

`docs/design-docs/core-beliefs.md` 에 두 앵커를 추가한다.

- `{#r-iface}` — 축 A 의 원칙과 임계 근거
- `{#r-struct-4}` — 축 C 의 원칙

훅 메시지가 이 앵커를 가리키므로, 앵커가 없으면 근거 링크가 거짓말이 된다.

## 검증

| 축 | 검증 방법 |
|---|---|
| A | 공개 심볼 8개짜리 새 `.py` 를 Write 시도 → **차단**. 7개 → 통과. `def main(` 제외 확인 |
| A | 이미 존재하는 파일에 Write(덮어쓰기) → 통과 (축 B 관할) |
| A | 상단 주석에 근거를 남긴 8개짜리 파일 → 통과 |
| A | `permissionDecision` 미지원 시 `additionalContext` 로 강등되는지 확인 |
| A | 삼중따옴표 문자열 안의 `def` 8개 → 통과 (정규식 구현이면 실패하는 케이스) |
| A | 문법이 깨진 `content` → 통과, 크래시 없음 |
| B | 비공개 헬퍼만 +5 추가 → **침묵** (현재는 오탐 발생). 공개 +5 → 경고 |
| B | 기존 델타 테스트가 계속 통과하는지 확인 |
| C | `export * from` 포함 배럴 → 차단. 선별 export 배럴 → 통과 |

## 미해결 — 구현 전 결정 필요

1. **축 A 의 하드 차단이 실제로 동작하는 Claude Code 버전.**
   `hookSpecificOutput.permissionDecision` 지원 여부를 구현 시 실측하고 결과를 기록한다.
   미지원이면 축 A 는 soft 로 강등되며, 그 경우 이 스펙의 목적(구조 우선 강제)이
   달성되지 않으므로 대안을 재설계해야 한다.
2. **축 C 의 적용 범위.** 현재 `R-struct` 는 Vue 컴포넌트 폴더 대상이다.
   Python `__init__.py` 까지 넓히면 대상 프로젝트가 달라진다.
3. **축 A 의 `.svelte` 처리.** `<script>` 블록의 `export let`(Svelte 4) 과 `$props()`(Svelte 5) 는
   컴포넌트 props 선언이지 모듈 인터페이스가 아니다. `^export ` 패턴을 그대로 쓰면
   props 개수가 인터페이스 폭으로 잘못 집계된다. 별도 처리가 필요하다.
