# Core Beliefs — 하네스 룰 앵커

> 본 문서는 hook 메시지가 가리키는 anchor 목록이다. 메시지는 짧게, 근거는 여기에.
> Opus 4.7 (2026-04-16+) 의 글자대로 해석 특성에 맞춰 hook 출력은 단일 권장 + 링크 형태.

## R5 — 우회 금지 {#r5}

pre-commit / hook 이 막으면 hook 또는 코드를 고친다. `--no-verify`, `eslint-disable` 단독 우회 금지.

## R-agent — 도메인 에이전트 우선 {#r-agent}

frontend/DB/TS 작업은 `fullstack-developer`, `database-reviewer`, `typescript-reviewer` 사용.
`general-purpose` 는 범용 조사·문서·검색 전용.

## R-size — 1 파일 = 1 책임 (500은 안전망) {#r-size}

**원칙**: 한 파일은 한 책임만 진다. 파일명이 그 책임을 드러내야 한다.
배럴 (`index.ts` / `__init__.py`) 로 import 인체공학을 유지.

**안전망**: soft 400 (PostToolUse 경고), hard 500 (pre-commit 차단).
이 한도가 트리거되면 *원칙이 상류에서 실패했다는 뜻* — 501줄에서 기계적 분리가
아니라 "왜 여기까지 왔지?" 부터 묻는다. 500 초과 파일은 거의 항상 책임 2개 이상이
섞여 있고, 제대로 분리하면 500 한도는 자연히 지켜진다.

정말 한 책임인데 500 을 넘으면 (큰 스키마 직렬화, 완전 열거 상태 머신 등) waiver 근거를
파일 상단 주석 + `docs/audits/` 에 기록 후 `.harnessrc` 의 `MAX_LINES_HARD` 상향.

## R-iface — 새 파일의 인터페이스 폭 {#r-iface}

**원칙**: 파일이 바깥에 약속하는 공개 심볼 수가 곧 인터페이스 폭이다.
좁은 인터페이스 뒤에 깊은 내부를 두는 것이 목표이며, 그 판단은 **파일을 만들기 전에** 한다.

**임계**: 새 파일의 공개 심볼 8개 이상이면 `PreToolUse(Write)` 에서 차단.
8 은 이 저장소 운영 코드 36개의 공개 심볼 분포에서 나왔다 —
7 이 최빈 고원(4개)이고 8부터가 상위 사분위다. 고원 안이 아니라 고원 바로 위에서 자른다.

**왜 R-size 로 부족한가**: 줄 수는 인터페이스 폭을 간접 추정하고, 그 추정이 뒤집혀 있었다.
`hermes-lifecycle.py` 는 은닉률 66%(공개 7/비공개 14)인데 483줄이라 500 한도에 가장 먼저 걸리고,
`hermes_loop.py` 는 공개 19/비공개 1 로 사실상 전부 노출인데 385줄이라 아무 신호도 못 받았다.
그리고 500줄에서 쪼개면 숨어 있던 헬퍼가 경계를 넘으며 공개로 승격돼 **더 얕아진다.**

**왜 차단인가**: `PreToolUse` 는 아직 아무것도 쓰이지 않은 시점이라 오탐 비용이 거의 0 이다.
같은 지표라도 커밋 시점에 막으면 완성된 코드의 재구성을 요구해 우회가 상시화된다.

**waiver**: 정말 한 책임이면 파일 상단 20줄 안에 `R-iface-waiver: <근거>` 주석을 남긴다.
우회 자체를 막는 것이 목적이 아니라 **우회하려면 이유를 적게 만드는 것**이 목적이다.

**검증 상태**: Provisional. 발화율을 관측해 과발화하면 임계를 재산정한다.
과발화하는 차단은 우회를 학습시키며, 그 학습은 되돌리기 어렵다.

## R-declare — 새 파일은 만들기 전에 책임을 적는다 {#r-declare}

> 검증 상태: **Provisional** (2026-08-25 도입, 발화율 관측 중)

**원칙**: 새 코드 파일을 만들려면 그 파일의 **유일한 책임**이 계획서 §4 에 한 문장으로
먼저 적혀 있어야 한다. 템플릿의 문구 그대로다 — *"위 목록을 먼저 못 쓰면 아직 설계가
덜 됐다는 뜻. 구현 들어가지 말 것."*

**왜 커밋이 아니라 Write 시점인가**: 커밋 시점에는 이미 파일이 있다.
"구조를 먼저 잡는다" 는 파일이 생기기 전에만 성립한다. `R-iface` 가 같은 자리에서
인터페이스 **폭**을 보고, 이 룰은 **책임 선언 여부**를 본다.

**왜 차단이 아닌가**: `R-iface` 의 "폭 8 이상" 은 이분 판정이라 차단할 수 있지만,
"이 파일이 계획에 있었어야 하는가" 는 기계가 판정할 수 없다. 스크래치·픽스처·긴급 수정이
정당하게 존재한다. 차단하면 우회가 상시화된다 — 알리되 막지 않는다.

**침묵 조건**: `active/` 에 계획이 하나도 없으면 말하지 않는다.
계획 부재는 `R-plan-missing` 의 관할이고, 같은 사실로 경고가 둘이 되면 둘 다 무시된다.
문서·설정·픽스처, 하네스 생성물(`scripts/hooks/`), 기존 파일 덮어쓰기도 대상이 아니다.

**템플릿 플레이스홀더는 선언이 아니다.** `path/to/file.ext` 가 그대로 남아 있으면
채우지 않은 것이며, 그것을 선언으로 세면 이 검사가 곧 무의미해진다.

## R-struct-4 — 배럴은 골라 내보낸다 {#r-struct-4}

**원칙**: 배럴(`index.js`/`index.ts`)에서 `export *` 금지. 필요한 심볼만 골라 내보낸다.

배럴은 은닉 장치가 아니라 **재노출 장치**다. 전부 내보내면 호출자가 알아야 할 심볼 수가
그대로여서 인터페이스가 하나도 좁아지지 않는다 — 개선되는 것은 import 경로의 길이뿐이다.
`R-iface` 가 "나눠라" 라고 해서 나눈 결과가 이 형태면 폭은 줄지 않는다.

`R-struct-1~3` 과 달리 컴포넌트 경로에 한정하지 않는다. 배럴 폭은 Vue 만의 문제가 아니다.
파이썬 `__init__.py` 는 pre-commit 이 검사기에 `.py` 를 넘기지 않아 아직 대상이 아니다.

**행동**: 차단. "전량 재export 인가" 는 이분 판정이라 `R-iface` 같은 임계 논쟁이 없다.

**검증 상태**: Provisional.

## R-cx — 순환 복잡도 {#r-cx}

**원칙**: 한 함수의 분기 수에 상한을 둔다. `R-size` 는 파일 크기만 보므로,
500줄을 지키면서 복잡도 48 짜리 함수를 쓰는 것이 통과하고 있었다.

**임계 12**: 저장소 함수 295개의 복잡도 분포에서 `11:11개 → 12:4개` 로 급락한다.
1~11 은 10~61개로 두텁게 이어지다 12 에서 끊긴다. 그 절벽에 임계를 놓는다.
영상 권고 6~8 을 쓰지 않은 것은 그것이 CRAP 스코어 기준이라 척도가 다르고,
이 저장소에서 임계 8 이면 68개(23%), 6 이면 101개(34%) 가 걸려 과발화하기 때문이다.

**라쳇**: `.cxbaseline` 이 기존 초과 파일의 현재값을 **허용 최대**로 동결한다.
일괄 적용하면 파일의 43% 가 막히고, 그 상태로 켜면 게이트를 끄는 것이 정상 작업 흐름이 된다.
기준선은 내려가기만 한다 — 개선되면 훅이 갱신을 안내하되 **스스로 고쳐 쓰지 않는다**
(훅이 워킹트리를 수정하면 커밋에 없는 변경이 생긴다).

`MAX_COMPLEXITY` 는 **이 값부터 차단**하는 임계이고, `.cxbaseline` 값은
그 파일에 **허용하는 최대값**이다. 둘의 경계가 한 칸 다르다.

**하네스는 자기가 배포한 파일의 기준선을 함께 보낸다.** 설치기가 `.cxbaseline` 의 항목 중
**프로젝트에 실제로 존재하는 경로**만 골라 프로젝트의 `.cxbaseline` 로 옮긴다.

이유는 실측이다(2026-08-25): 하네스는 복잡도 48짜리 `scripts/hermes-search.py` 를 11개
프로젝트에 배포하는데, 기준선 없이 R-cx 를 켜면 **사용자가 쓰지도 않은 코드 때문에**
하네스 갱신 커밋이 막힌다. 자기 코드가 완전히 깨끗한 프로젝트 3개조차 막혔다.

**면제가 아니라 기록 이전이다.** 경로를 R-cx 대상에서 빼면 그 파일들은 영원히 검사 밖이
된다 — `R-test` 가 죽어 있던 방식이다. 값을 동결하면 계속 검사받되 현재 상태는 통과하고,
하네스가 나빠지면 하류에서도 잡힌다.

**설치 시 그 프로젝트의 기존 위반도 함께 동결한다.** 하네스 기준선은 하네스 파일만 덮으므로,
프로젝트가 원래 갖고 있던 복잡한 함수는 아무도 동결해 주지 않는다. 그대로 켜면 그 파일을
건드리는 커밋이 전부 막히고, 이 절이 이미 경고한 상태가 된다 —
"게이트를 끄는 것이 정상 작업 흐름이 된다".
실측(2026-08-25): rim-office 45개 · upbit-ai-trading 42개 · kis-trading 36개 · novel-ab 13개.

임계 **미만** 파일은 넣지 않는다. 넣으면 현재값이 그 파일의 상한이 되어 오히려 더 조인다.
그리고 **조용히 얼리지 않는다** — 설치 로그가 동결 개수와 목록 위치를 알린다.
부채가 보이지 않으면 게이트가 죽은 것과 같다.

병합은 **min 으로만** 한다. 더 높은 값으로 덮으면 프로젝트가 동결한 값이 조용히 느슨해진다.
배포 파일 목록을 따로 들고 다니지 않는 것도 같은 이유다 — 목록은 배포가 바뀌면 어긋난다.
언인스톨은 `.cxbaseline` 을 지우지 않는다. 사용자 항목이 섞여 있고, 사라진 경로의 항목은
검사기가 건너뛰므로 무해하다.

**검증 상태**: Provisional.

## R-dep — 모듈 의존 계약 {#r-dep}

**원칙**: 모듈 사이의 의존 방향을 `.deprc` 에 고정한다. tier 번호가 큰 쪽이 상위이며
하위는 상위를 import 할 수 없다. 같은 tier 안의 상호 참조는 허용한다.

| 규칙 | 내용 | 행동 |
|---|---|---|
| `R-dep-1` | 계층 역전 | 차단 |
| `R-dep-2` | 순환 의존 | 차단 |
| `R-dep-3` | `forbid:` 경계 위반 | 차단 |
| `R-dep-4` | `scope:` 안인데 tier 미등록 | 경고 |

**계약은 발명이 아니라 고정이다.** tier 는 손으로 적은 것이 아니라 2026-08-24 실측
그래프에서 위상적으로 계산했다. 도입 시점의 위반은 0건이다.

**AST 로 검사한다.** 첫 측정을 정규식으로 했다가 들여쓴 import 를 전부 놓쳤다 —
전체 간선의 3분의 1이었고, 그중 하나가 초안의 `forbid` 규칙을 위반하는 의도된 설계였다.
파이썬의 조건부·지연 import 는 함수나 `try` 블록 안에 있어 들여쓰기가 기본이다.

**선택적 의존**: `try/except ImportError` 로 감싸 없어도 동작하는 import 는 `optional:` 로
등록해 면제받는다. 다만 **등록만으로는 면제되지 않는다** — 검사기가 `try` 블록 여부,
`ImportError` 핸들러 여부, fallback 할당 여부를 확인한다.
등록이 곧 면제면 `optional:` 한 줄 추가가 우회 경로가 된다.

**계약 부재는 조용하다.** 고장이 아니라 미설정이기 때문이다. `R-test` 는 *켜져 있는데*
아무것도 안 막으면서 통과 표시를 냈고 그것이 문제였다. 여기서는 사용자가 계약을 만든 적이 없다.
계약 없는 프로젝트에 매 커밋 경고를 내면 경고 피로로 훅이 꺼진다 — 안내는 설치 시점에 한 번 한다.

**검증 상태**: Provisional.

## R-fmt — 포맷팅 {#r-fmt}

prettier 위반은 `pnpm exec prettier --write` 로 자동 수정. `.prettierrc` 단독 변경 금지 (프로젝트 합의 필요).

## R-lint — ESLint {#r-lint}

ai-dev-setting 의 lint 룰 메시지에는 한국어 수정 지침이 박혀있음. 메시지 따라 수정. `eslint-disable` 단독 우회 금지.

## R-test — pytest {#r-test}

`tests/` 또는 `backend/tests/` 가 있으면 커밋 전 pytest 를 돌린다. **세 상태를 구분한다.**

| 상태 | 판정 | 이유 |
|---|---|---|
| 테스트 실패 | **차단** | 회귀다 |
| 수집 0개 (exit 5) | 경고 | 파이썬 없는 프로젝트도 설치 대상이라 막으면 안 된다 |
| pytest 실행 불가 | 경고 | 도구가 못 뜬 것이지 코드 문제가 아니다 |

**왜 수집 0개를 경고하는가**: 이 저장소는 파이썬 단위 테스트가 0개인 채로
`R-test` 가 늘 통과하고 있었다. exit 5 를 통과로 두는 판단 자체는 옳지만,
**그 예외 경로에 영구히 머물러 있다는 사실을 아무도 몰랐다.**
게이트가 죽은 줄 모르는 것이 게이트가 없는 것보다 나쁘다.

**왜 실행 불가를 구분하는가**: 예전에는 "pytest 가 자기 모듈을 import 못 하는 상태" 가
`[R-test] pytest 실패` + Traceback 으로 보고되며 커밋을 막았다. 사람은 자기 코드를 뒤지게 된다.
실측(2026-08-24): `HOME` 이 바뀌어 user-site 가 사라지면 실행 파일은 있는데 import 가 깨진다.

## R-cov — 테스트가 실행하지 않는 코드 {#r-cov}

> 검증 상태: **Provisional** (2026-08-25 도입, 발화율 관측 중)

**원칙**: 스위트 전체를 돌려도 **한 줄도 실행되지 않는** 파일을 고치면 경고한다.
`R-test` 는 "테스트가 실패했는가" 만 본다. 통과했다고 그 커밋의 코드가 검증됐다는 뜻은 아니다.

**임계를 두지 않는다.** 2026-08-25 실측(운영 파이썬 37개, bash 통합 테스트 35종 기준)에서
0% 와 그 다음 값 사이가 **70.6 포인트** 벌어진 반면 나머지는 70.6~100 사이에 촘촘히 이어진다.
두 번째로 큰 간격이 5.2 포인트뿐이라 "몇 % 이상" 을 가를 자연스러운 자리가 없다.
자를 곳은 하나뿐이다 — **한 번이라도 실행되는가.** `R-dep` 과 같은 이분 판정이다.

문서 7곳이 말하는 "80%" 를 쓰지 않는다. 적용하면 70.6·72.4·77.6 세 파일이 걸리는데,
분포상 이들은 82~86 무리와 구분되지 않는다. 출처가 불명확한 관습값이고 근거 없는 경계다.

**외부 패키지를 쓰지 않는다.** `assets/hooks/coverage_probe.py` 가 표준 라이브러리 `trace` 로
측정한다. 하네스는 여러 프로젝트에 설치되는 도구라, 설치 요구가 곧 게이트 침묵이 된다.
전역 설치는 머신마다 결과가 갈리고, 프로젝트별 venv 는 하네스가 프로젝트의 런타임
의존성 관리를 떠맡는 것이다 — 선택지를 고르는 대신 의존을 없앴다.

**하위 프로세스를 추적한다.** 이 저장소의 검증 수단은 파이썬을 자식 프로세스로 띄우는
bash 통합 테스트라, 부모만 보면 전부 0% 로 나온다. `PYTHONPATH` 의 `sitecustomize.py` 가
인터프리터마다 추적을 붙인다. **테스트가 `PYTHONPATH` 를 덮어쓰면 그 프로세스는 측정에서
빠진다** — 첫 실측에서 `hermes_mesh_gate.py` 가 전용 테스트 24/24 통과 상태로 0% 를 기록했다.
게이트가 거짓 신고를 할 뻔했고, `tests/coverage-probe-test.sh` 가 그 회귀를 고정한다.

**측정은 사람이 돌린다.** 스위트 전체 실행에 수 분이 걸려 커밋 훅이 직접 잴 수 없다.
결과는 `.covbaseline` 에 남긴다(`.cxbaseline` 과 같은 방식). 파일이 없으면 조용히 통과한다 —
미설정은 고장이 아니다. 측정 기록에 없는 새 파일도 판정하지 않는다: 모른다는 것과
0% 라는 것은 다르다.

## R-mut — 테스트의 유효성 {#r-mut}

> 검증 상태: **진단 도구** (게이트 아님). 2026-08-25 도입.

**원칙**: 테스트가 **있다**는 것과 회귀를 **잡는다**는 것은 다르다.
소스의 연산자를 뒤집고 기존 테스트가 실패하는지 본다 — 통과하면 그 경로에 단언이 없다는 뜻이다.

**게이트가 아니다.** 8개 모듈 전수 실행이 수십 분이라 커밋 경로에 맞지 않고,
실측 분포(59.1~90.0%)에 자를 만한 절벽이 없다. 임계를 만들지 않는다.
생존 변이 목록을 **테스트를 추가할 지점** 목록으로 쓴다.

실행: `python3 scripts/mutation-probe.py --target <파일> [--test <테스트>]`
`--test` 를 생략하면 이름 규칙(`hermes_loop.py` → `hermes-loop-test.sh`)으로 찾는다.
종료코드 0=생존 있음 / 1=전부 잡힘 / 2=판정불가.

**복원이 이 도구의 안전 요건이다.** 소스를 망가뜨린 채 종료하는 도구는 사고다.
`try/finally` + 시그널 핸들러(INT/TERM/HUP) + 종료 시 내용 대조, 세 겹으로 건다.
`tests/mutation-probe-test.sh` 가 테스트 크래시·도구 SIGTERM 두 경로에서 복원을 단언한다.

**베이스라인을 먼저 본다.** 원본 상태에서 이미 실패하는 테스트로는 모든 변이가
killed 로 나와 **거짓 100%** 가 만들어진다. 그 경우 판정불가(2)로 끊는다.

**tokenize 로 변이 지점을 찾는다.** 라인 정규식이면 주석·문자열 안의 `>=`·`and` 까지
세고, 그 변이는 의미가 안 바뀌어 전부 생존으로 보고돼 노이즈가 신호를 덮는다.
`R-cx`·`R-dep`·`R-iface` 가 AST 를 쓰는 것과 같은 이유다.

**커버리지와 겹치지 않는다.** 첫 실측에서 8개 모듈은 전부 커버리지 70% 이상이었는데
변이의 26% 가 살아남았다. 커버리지는 *줄이 실행됐는가*, 변이 점수는 *그 줄이 틀렸을 때
누가 우는가* 를 본다.
실측 요약은 `docs/superpowers/specs/2026-08-24-ai-engineering-gap-roadmap.md` 의 `R-mut` 절에 있다
(생존 변이 전체 목록은 `docs/audits/` 에 남기며, 이 디렉터리는 로컬 전용이다).

## R-review — 리뷰 빚 {#r-review}

코드 수정 발생 시 `.claude/.review-dirty` 생성. 자연 단위(엔드포인트/컴포넌트/마이그레이션 한 단락) 종료 시
code-reviewer dispatch 후 청산. 청산은 `claude-posttooluse-review-record.sh` 가 자동으로 한다 —
`subagent_type` 이 `-reviewer` 로 끝나는 dispatch 를 감지해 기록을 지운다. 수동 청산은 `rm .claude/.review-dirty`.

**강제 (`R-pipe`, Provisional)**: 리뷰 기록이 남은 파일이 커밋에 포함되면 `pre-commit` 이 **경고**한다.
차단이 아닌 이유는 훅이 "리뷰어를 불렀다"까지만 알 수 있고 "리뷰가 유효했다"는 알 수 없기 때문이다 —
확인 못 하는 것을 차단 조건으로 삼으면 리뷰어를 부르고 결과를 무시하는 형식적 통과를 학습시킨다.

> 2026-08-24 정정: 이 문단은 오래 "안 지우면 commit 단계에서 차단" 이라고 적혀 있었으나
> `pre-commit` 은 `.review-dirty` 를 **한 번도 읽지 않았다.** 존재하지 않는 강제를 문서가 주장한 것으로,
> `R-test` 가 테스트 0개로 늘 통과하던 것과 같은 결함이다. 실제 강제(경고)를 붙이면서 문구를 맞췄다.

**도메인 리뷰어 병렬 dispatch (조건부)**: 변경에 DB 스키마/마이그레이션이 포함되면 `code-reviewer` 와 `database-reviewer` 를
*병렬로 함께* dispatch 한다. code-reviewer 는 Task 도구가 없어 스스로 위임할 수 없으므로 오케스트레이터가 책임.
DB 변경이 없는 단위는 단독 dispatch 유지 — 무차별 병렬 호출 금지.
강제: `assets/hooks/claude-pretooluse-agent-guard.sh` 가 code-reviewer dispatch 의 prompt/description 에서
DB 키워드 감지 시 additionalContext 로 안내 주입.

## R-plan — 완료된 계획 이동 강제 {#r-plan}

`docs/exec-plans/active/*.md` 의 모든 체크박스가 `[x]` 이면 pre-commit 차단.
회고(§8) 작성 후 `git mv active/<plan>.md completed/` 로 마감. 상세: `docs/exec-plans-system.md`.

**backlog/**: 아직 일정이 없는 작업 후보. 날짜 없이 `<slug>.md` 로 보관. active/ 로 승격 시 날짜 prefix 추가.

## R-acc — 실행 가능한 인수 조건 {#r-acc}

> 검증 상태: **Provisional** (2026-08-25 도입, 발화율 관측 중)

계획서 §2 의 목표는 산문이 아니라 **목표 + 그것을 확인하는 명령** 쌍으로 쓴다.
템플릿이 §2 에 "검증 가능한 형태"를 이미 요구해 왔으나 형식이 없어 산문으로 채워졌고,
그 문장이 실제로 검증되는지는 어느 룰도 보지 않았다.

| 규칙 | 검사 | 행동 |
|---|---|---|
| `R-acc-1` | 스테이징된 `active/` 계획서 §2 목표에 검증 명령이 없음 | 경고 |
| `R-acc-2` | `completed/` 로 옮기는데 §2 목표가 미완(`[ ]`) | 경고 |

**둘 다 경고다.** `R-retro` 와 같은 한계 — 기계는 "쓰지 않았음"까지만 본다.
명령이 적혀 있다는 사실이 그 명령이 통과한다는 뜻은 아니다.

**훅은 그 명령을 실행하지 않는다.** 계획서는 에이전트가 쓰는 파일이므로, 거기 적힌 것을
커밋 훅이 실행하는 구조는 게이트가 게이트 대상에게 실행 권한을 넘기는 것이다.

**Gherkin 을 쓰지 않는 이유**: 실행에 프레임워크(`behave`, `pytest-bdd`)가 필요한데
하네스는 여러 프로젝트에 설치되므로 프레임워크 요구는 곧 설치 실패 = 게이트 침묵이다.
또 이 저장소의 검증 수단은 이미 bash 테스트라, 별도 명세 언어를 얹으면 검증이 두 곳으로 갈라진다.

**범위**: `R-acc-1` 은 **스테이징된** 계획서만 본다. `active/` 전체를 훑으면 옛 형식의
남의 계획서까지 걸려 무관한 커밋이 매번 경고를 받는다 — `R-plan` 이 2026-07-23 에
같은 이유로 좁힌 범위와 동일하다.

## R-plan-missing — 코드 수정 시 계획 존재 {#r-plan-missing}

코드 파일 수정이 있는데 `active/` 에 계획이 없으면 경고(차단 아님).
단순 버그 수정은 무시. 다중 파일·설계 결정이면 `docs/exec-plans/active/YYYY-MM-DD-<slug>.md` 작성. 템플릿: `docs/exec-plans/template.md`.

## R-plan-stale — 계획서가 코드를 따라오는가 {#r-plan-stale}

`active/` 에 계획서가 있는데 작업 코드만 스테이징되면 경고(차단 아님).

R-plan 은 *스테이징된* 계획서만 검사한다 — "갱신하지 않는 행동" 을 잡으려는 장치가
"갱신했음" 을 전제하는 순환 의존이었다. 이 룰이 그 축을 뒤집는다.

**차단하지 않는 이유**: 계획서가 하나뿐일 때 차단하면 워킹트리 공유 시 상호 차단이
발생한다(2026-07-23 사고, `tests/harness-hooks-smoke.sh` 13(a) 가 회귀를 고정한다).
일부라도 스테이징돼 있으면 통과시킨다 — 어느 계획에 속한 커밋인지 훅은 알 수 없다.
하네스 생성물(`scripts/hooks/`)은 대상에서 제외한다: 재설치가 덮어쓰므로 포함하면
하네스 갱신 커밋이 자기 게이트에 걸린다.

**검증 상태**: Provisional. 오탐 데이터를 `docs/audits/` 에 쌓은 뒤 차단 승격을 검토한다.

## R-retro — 회고 없이 완료 처리 금지 {#r-retro}

`completed/` 로 **옮긴** 계획서의 §8 이 템플릿 그대로 비어 있으면 경고(차단 아님).

완료 처리의 실질이 파일 경로 이동뿐이어서 회고가 선택 사항이 되어 있었다.

`git diff --cached --diff-filter=RA` 로 이동(rename·신규)만 본다. `git mv` 는 `ACM` 필터에
잡히지 않으므로(2026-08-13 실측) `STAGED` 를 쓸 수 없고, `M`(수정)을 넣으면 옛 계획서의
오타 수정까지 걸려 하지도 않은 작업의 회고를 지어내게 된다.

**한계**: 기계는 "쓰지 않았음" 까지만 본다. 회고의 품질은 판정하지 않는다.
이미 `completed/` 에 쌓인 것은 주간 가드닝의 `[plan-noretro]` 가 수거한다.

**검증 상태**: Provisional.

## P9 — 비밀의 경계는 파일이 아니라 값이다 {#p9}

**원칙**: 자격증명·개인정보를 평문으로 커밋하지 않는다. git 히스토리는 되돌릴 수 없으므로
*들어가기 전에* 막는 것이 유일한 방어다.

**왜 파일 단위 규칙으로는 부족한가**: "`.env` 를 커밋하지 않는다"는 규칙이 완벽히 지켜지는
동안에도, 같은 값이 **채팅 텍스트**로 전달되는 순간 규칙의 사정권 밖으로 나갔다. 실제로
그렇게 새어 세션 기록 파일에 실려 커밋·푸시까지 갔다.

**따르는 규칙 셋**:
- **값 대조가 형태 추측에 우선한다.** `label=value` 딱지를 전제한 마스킹은 사람이 실제로
  주는 형태(`아이디 | 비번`)를 원리상 못 잡는다. `.env` 실재 값을 정답지로 대조한다.
- **면제 규칙은 탐지 단위와 같은 폭이어야 한다.** 줄 단위 탐지에 줄 단위 자리표시자 면제를
  붙이면, 한 줄이 긴 파일(jsonl)에서 `example` 한 번에 그 줄의 진짜 비밀이 통째로 면제된다.
- **패턴을 복제하면 역류 경로를 함께 정한다.** 복제본에서 구멍을 고치고 원본을 두면,
  원본을 쓰는 경로가 계속 뚫려 있다.

**기계 강제**: `pre-commit` R-secret 단계(`check-secrets.py`) + DB·export 경계
마스킹(`hermes_redact.py`). 회귀 고정: `tests/hermes-secret-masking-test.sh`.
소급 정리: `scripts/hermes-scrub-history.py`. 상세: `docs/superpowers/specs/2026-08-10-hermes-secret-masking-design.md`.
