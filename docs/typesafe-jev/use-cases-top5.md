## 1. 비정형 문서·영수증·인보이스 초고속 스키마 추출 (ETL) — 23–24쪽

기존 OCR·LLM 파이프라인에서 돈과 시간이 가장 많이 들던 정형화 단계를 대체한다.

- **동작 방식**: 수십 장짜리 PDF 나 긴 텍스트 문서 전문을 Jev 의 `state` 로 한 번에 넣고, 필드별 질문을 병렬로 던진다.
  - Q1: "발행일자가 명시되어 있는가? 있다면 ISO-8601 포맷 값은?"
  - Q2: "최종 결제 통화는 KRW, USD, EUR 중 무엇인가?"
- **기존과의 차이**: Claude 나 GPT 에게 전체 JSON 을 뽑게 하면 5~10초 동안 토큰을 생성하며 기다리지만, Jev 는 필드 값을 각각 0.1초 만에 병렬로 타입화해 돌려준다.
- **신뢰도 활용**: 신뢰도 0.95 이상 필드는 DB 에 즉시 자동 저장, 0.7 미만으로 떨어진 필드만 관리자 검토 큐로 넘긴다.
- 앞 목록(15–18쪽)에는 없던 사례다.
- 걸리는 점: Q1 의 "ISO-8601 값은?" 은 날짜 **값을 만들어 내는** 질문이다. 공식 질문 종류(Choice·Score·Noul)는 고르기·점수·참거짓뿐이라, 이 질문이 그대로 되는지는 공식 문서로 확인하지 못했다.

## 2. 멀티 에이전트 시스템의 "지능형 트래픽 라우터" — 24쪽

사용자 프롬프트를 어떤 전용 모델·도구로 넘길지 정하는 교통정리 역할이다.

- **동작 방식**: 요청을 분석해 다음 수행 경로를 Enum 으로 가른다.

```typescript
type RouteDecision = {
  target: "SIMPLE_SQL" | "VECTOR_SEARCH" | "HEAVY_REASONING" | "DI…  // [잘림]
  estimated_difficulty: 1 | 2 | 3;
  confidence: number;
};
```

- **기존과의 차이**: LangChain 등은 라우팅에 고가 LLM 을 불러 첫 응답 지연(TTFT)이 1~2초씩 생겼다. Jev 를 라우터로 두면 50ms 만에 단순 작업(SQL 실행·문서 조회)과 복잡한 작업(Opus/Sonnet 호출)을 갈라 전체 지연을 크게 줄인다.
- **앞 목록 판(17쪽)과 비교**:

```typescript
type AgentRoute = {
  target: "SQL_AGENT" | "SEARCH_AGENT" | "REFACTOR_AGENT" | "…  // [잘림]
  estimated_complexity: 1 | 2 | 3 | 4 | 5;
}
```

| 항목 | 17쪽 판 | 24쪽 판 (Top 5) |
|---|---|---|
| 타입 이름 | `AgentRoute` | `RouteDecision` |
| 보낼 곳 | 에이전트 단위 (`SQL_AGENT` 등) | 작업 단위 (`SIMPLE_SQL`·`HEAVY_REASONING` 등) |
| 난이도 | `estimated_complexity` 1~5 | `estimated_difficulty` 1~3 |
| 신뢰도 필드 | 없음 | `confidence` |
| 효과 | 라우팅용 Sonnet/GPT-4o 호출을 완전히 대체, TTFT 1초 이상 단축, 비용 거의 0 | TTFT 1~2초 → 50ms |

## 3. 실시간 트랜잭션 이상 감지·어뷰징 차단 (Fraud Detection) — 24–25쪽

결제·로그인·부정 거래 감지에서 규칙 기반 필터와 머신러닝 사이의 빈자리를 채운다.

- **동작 방식**: 유저의 최근 행동 로그, IP 변경 이력, 결제 시도 메타데이터 덤프를 넣고 위험도를 판별한다.
- **신뢰도 활용 (RLCD 의 강점)**:
  - 위험 확률 0.98 이상 → 결제 즉시 차단
  - 위험 확률 0.50~0.85 → 추가 본인인증(OTP/SMS)
  - 위험 확률 0.15 이하 → 무검사 통과
- **기존과의 차이**: 초당 수백 건이 오가는 환경에서 고가 LLM 은 비용이 감당되지 않지만, Jev 는 모든 트랜잭션을 전수 조사해도 부담이 거의 없다.
- **앞 목록 판(17–18쪽)과 비교** — 구간 경계가 다르다:

| 구간 | 17–18쪽 판 | 25쪽 판 (Top 5) |
|---|---|---|
| 자동 차단 | 0.99 이상 | 0.98 이상 |
| 추가 인증 | 0.60~0.85 | 0.50~0.85 |
| 무검사 통과 | 0.20 이하 | 0.15 이하 |
| 입력 | 최근 **10회** 행동 로그 · IP 변경 이력 · 결제 메타데이터 | 최근 행동 로그 · IP 변경 이력 · 결제 메타데이터 |

- 걸리는 점: **두 판 모두 구간 사이에 빈틈이 있다.** 25쪽 판 기준 0.15~0.50 과 0.85~0.98 에 해당하는 거래를 어떻게 할지 정하지 않았다. 돈이 걸린 판정이라 실제로 쓰려면 이 빈 구간의 처리부터 정해야 한다.

## 4. CI/CD 배포 로그 실시간 서킷 브레이커 — 25쪽

테스트 실패나 빌드 에러 로그를 보고 배포를 멈출지 정하는 파이프라인 필터다.

- **동작 방식**: 수천 줄의 Docker 빌드 로그나 유닛 테스트 스택 트레이스를 넣는다.

```typescript
type BuildVerdict = {
  is_transient_network_error: boolean; // 일시적 네트워크 타임아웃인가
  is_code_defect: boolean;             // 코드/문법 결함인가?
  should_retry: boolean;
};
```

- **기존과의 차이**: 정규식은 새 형태의 로그를 놓치기 쉽고, LLM 을 부르면 빌드가 늦어진다. Jev 는 비정형 로그를 0.1초 만에 읽고, 일시적 네트워크 에러면 자동 재시도, 코드 에러면 배포를 멈추고 슬랙 알림을 보낸다.
- **앞 목록 판(16–17쪽)과 비교**:

```typescript
type ErrorClassification = {
  is_transient: boolean;      // 일시적 네트워크/DB 타임아웃인가?
  requires_rollback: boolean; // 즉시 롤백해야 할 코드 결함인가?
  risk_level: "LOW" | "HIGH" | "CRITICAL";
  confidence: number;
}
```

| 항목 | 16–17쪽 판 | 25쪽 판 (Top 5) |
|---|---|---|
| 판정 필드 | 일시 오류 · 롤백 필요 · 위험 3등급 | 일시 네트워크 오류 · 코드 결함 · 재시도 여부 |
| 신뢰도 | `confidence` 필드, 0.95 이상이면 알림 없이 자동 재시도 | 필드 없음 |
| 대상 | 단위 테스트 실패 로그 · 서버 500 스택 트레이스 | Docker 빌드 로그 · 유닛 테스트 스택 트레이스 |

- 걸리는 점: 25쪽 판은 `is_transient_network_error` 와 `should_retry` 가 따로 있어 둘이 어긋날 수 있다(일시 오류인데 재시도 안 함). 어느 쪽을 따를지 정해야 한다.

## 5. 대규모 유입 티켓 실시간 감정·우선순위 분류 — 25–26쪽

Zendesk, 슬랙 고객 채널, 이메일로 들어오는 대량의 고객 문의를 자동 분류한다.

- **동작 방식**: 긴 불만 글이 들어오면 감정 분석을 길게 쓰지 않고 플래그만 뽑는다.

```json
{ "churn_risk": true, "urgency": "IMMEDIATE", "dept": "ENTERPRISE_BILLING" }
```

- **기존과의 차이**: 키워드 매칭은 문맥의 뉘앙스를 놓치지만, Jev 는 문맥을 읽으면서도 JSON 파싱 실패나 환각 없이 정해진 필드만 바로 돌려줘 실시간 웹훅 핸들러에 지연 없이 붙는다.
- **앞 목록 판(18쪽)과 비교**:

```json
{ "churn_risk": true, "department": "ENTERPRISE_SUPPORT", "urgent": true }
```

| 항목 | 18쪽 판 | 26쪽 판 (Top 5) |
|---|---|---|
| 긴급도 | `urgent: true` (참거짓) | `urgency: "IMMEDIATE"` (등급) |
| 부서 필드 | `department` | `dept` |
| 부서 예 | `ENTERPRISE_SUPPORT` | `ENTERPRISE_BILLING` |
| 효과 | 1B 당 $42 라 수만 건 웹훅도 전수 조사 | 파싱 실패·환각 없이 웹훅 핸들러에 바로 연결 |

## 공통 관통점 (26쪽, 18쪽)

- 26쪽: "LLM 의 긴 자연어 생성(답변 작성) 기능은 완전히 버리고, 비정형 텍스트를 읽고 IF/ELSE 조건문에 넣을 True/False 나 Enum 만 뽑아내는" `[잘림]` — 문서가 여기서 끝난다.
- 18쪽의 같은 취지 문장: "결과물로 긴 글(문장)을 받아야 하는 곳에는 절대 쓰지 말고, IF/ELSE 조건문에 들어갈 boolean 이나 enum 값을 뽑는 자리에 집어넣어라."
