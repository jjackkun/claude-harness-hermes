# Jev 활용 사례 — Playwright 브라우저 에이전트

> 작성일: 2026-09-21
> 목적: PDF 에 흩어진 Playwright(브라우저 자동화) 관련 내용을 한 문서로 모은다.

## 개요

- 출처: `docs/temp/how to zev.pdf` 16쪽(Threads 사례 1번), 21–22쪽(토큰 질문), 23쪽("너무 좋은데?" 답).
- 여기 적힌 속도·비용·효과는 **PDF 의 챗봇이 한 말**이고 확인하지 않았다. 원 게시물 링크도 PDF 에 없다. 확인 상태는 [fact-check.md](fact-check.md).
- 공식으로 확인된 것은 입력가 $42 / 10억 토큰, 속도 예시 0.114 s 대 8.566 s, 질문 종류 Choice·Score·Noul 뿐이다.

## 1. 무엇을 하나 — "다음 액션 결정" (16쪽)

PDF 는 Threads 사례 중 "가장 반응이 뜨거웠던 분야" 라고 소개했다. Playwright·Puppeteer 와 연결한 자동화 에이전트 루프다.

### 동작 방식

- 웹페이지의 DOM 트리 전체(수십~수백 KB)를 그대로 Jev 의 `state` 로 넣는다.
- 묻는 질문 예:
  - "로그인 폼을 채우기 위해 다음으로 클릭해야 할 요소의 셀렉터는?"
  - "페이지네이션 '다음' 버튼이 활성화되어 있는가?"

### 차별점

- 기존에는 페이지가 바뀔 때마다 Claude/GPT 를 불러 3~5초씩 기다렸다.
- Jev 는 0.1초 만에 다음 행동을 열거형으로 돌려준다: `CLICK` · `WAIT` · `SCROLL` · `FINISH`.
- **하이브리드**: confidence 가 0.8 미만으로 떨어질 때만 고가 Vision LLM 을 불러 스크린샷을 보게 한다. 이 방식으로 크롤러 속도를 10배 이상 올렸다고 한다.

## 2. 시간뿐 아니라 토큰도 줄어드나 (21–22쪽)

사용자 질문: "Playwright 의 시간을 단축한다는데 토큰도 줄어드는 건가?" → 챗봇 답: "네, 토큰 비용도 압도적으로 줄어듭니다." 이유 둘을 들었다.

### 이유 1 — 출력 토큰이 거의 0

| 방식 | 출력 |
|---|---|
| 일반 LLM (Claude/GPT) | 다음 행동을 정할 때 "현재 화면의 장바구니 버튼은 상단 네비게이션에 위치하므로…" 같은 생각 과정(CoT)과 긴 JSON 을 낸다. 턴당 수십~수백 출력 토큰, 출력 단가는 입력의 3~5배 |
| Jev | 긴 텍스트 없이 `Enum` 이나 `Selector ID` 같은 단일 결정 값만 낸다. 출력 요금은 무료 |

### 이유 2 — 대화 기록 누적이 없다

| 방식 | 입력 |
|---|---|
| 일반 챗봇형 에이전트 | `Page 1 열림 ➔ 버튼 클릭함 ➔ Page 2 로딩됨` 같은 이전 단계를 대화 기록으로 계속 쌓아 다음 턴에 다시 넣는다. 10스텝만 넘어가도 세션 하나에 수백만 토큰 |
| Jev (System One) | 대화 기록을 들고 있지 않는 무상태(Stateless) 결정기. 현재 DOM 과 질문만 넣으므로 누적 낭비가 없다 |

## 3. 비용 비교 — 10단계 브라우징 (22쪽)

조건: 복잡한 웹페이지 DOM 약 20,000 토큰을 읽으며 10번 연속 클릭·입력.

| 구분 | Claude 3.7 Sonnet | TypeSafe Jev |
|---|---|---|
| 입력 토큰 비용 | 약 $0.60~$1.20 (기록 누적 시) | 약 $0.0084 (누적 없이 현재 상태만) |
| 출력 토큰 비용 | 약 $0.05~$0.15 | $0.00 (무료) |
| 소요 시간 | 턴당 2~4초 → 총 30초 이상 | 턴당 0.1초 → 총 1~2초 |
| 총비용 | 약 $0.70~$1.35 (약 1,000~1,800원) | 약 $0.008 (약 11원) |

- 결론(챗봇): 시간과 함께 비용도 약 1/100 로 준다.
- 검산: Jev 입력 20,000 토큰 × 10회 = 200,000 토큰 × $0.042 / 100만 = **$0.0084** — 표의 Jev 입력 비용과 맞는다.
- 주의: 비교 대상이 "Claude 3.7 Sonnet" 이라는 옛 모델이다. Claude 쪽 수치는 대조하지 않았다.

## 4. 챗봇이 권한 쓰는 법 (23쪽)

사용자가 "너무 좋은데?" 라고 하자 챗봇이 정리한 세 가지:

- **속도**: 턴당 2~4초 루프가 0.1초로 내려가면 브라우저 자동화가 네이티브 스크립트처럼 돈다.
- **비용**: 매달 $5 크레딧으로 개인용 크롤링·라우팅은 사실상 무제한에 가깝게 테스트할 수 있다.
- **신뢰도 연계**: 신뢰도 0.7 이하에서만 고가 LLM 으로 넘기는 예외 처리를 두면 안정성과 경제성을 함께 챙긴다.

- 시작 방법: 콘솔의 `Try an example request` 에서 키를 받아 가벼운 라우팅·분기 스크립트부터 붙여 본다.

## 5. 읽을 때 걸리는 점

- **임계값이 두 개다.** 16쪽은 0.8 미만에서 Vision LLM 으로 넘긴다고 했고, 23쪽은 0.7 이하에서 고가 LLM 으로 넘기라고 했다. 둘 다 근거가 제시되지 않았다. 과제마다 실측해서 정할 값이다.
- **"수백 KB DOM 을 그대로" 넣을 수 있는지**는 입력 한도에 달렸다. 공식 문서에서 입력 한도를 찾지 못했다([fact-check.md](fact-check.md)).
- **무상태가 늘 이득은 아니다.** 여러 페이지에 걸친 목표(예: 3단계 결제 흐름)에서는 "지금 어디까지 했나" 를 호출하는 쪽 코드가 `state` 에 직접 넣어 줘야 한다. PDF 는 이 부분을 다루지 않는다.
- **이 사용자와의 관계**: 저장소 코드에는 Playwright 루프가 없지만(`assets/skills/webapp-testing/examples/` 예제 3개뿐), **Claude Code 세션이 Playwright MCP 로 바로 이 루프를 돌고 있다** — 2,794턴 · 입력 약 13억 토큰 · 단계당 컨텍스트 46.5만. PDF 의 표(Claude 턴당 기록 누적)가 이 사용자의 기록에서 실제로 나타난다. 측정과 구조는 [playwright-in-sessions.md](playwright-in-sessions.md).
