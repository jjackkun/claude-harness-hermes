## 1단계. 프롬프트 엔지니어링 (2023~)

> "어떻게 물어봐야 좋은 답이 나올까?"

### 핵심 아이디어

모델은 그대로 두고 **질문(프롬프트)을 정교하게 설계**하는 단계다. 역할 부여, 예시 제시(few-shot), 단계적으로 생각하라는 지시 — 전부 **한 번의 질문 안에서 승부를 본다.**

### 그래프 구조

```
사용자 (프롬프트 한 방) → LLM (학습 시점의 기억만) → 분석 리포트 (일반론 · 재현 불가)
                                 ⚠ 최신 시세·공시 모름
```

### 예시 프롬프트

```text
"너는 20년차 반도체 애널리스트야. 삼성전자를 SWOT으로 분석하고,
 단계적으로 추론해서 목표주가를 제시해줘."
```

### 실행 로그 (데모 재생 결과)

```
[00.4s] 사용자 프롬프트 입력: "너는 20년차 애널리스트야. 삼성전자를 분석하고 목표가를 제시해줘"
[01.6s] LLM 호출 | 컨텍스트: 프롬프트 1건 (외부 데이터 0건)
[03.2s] 응답 생성: "...안정적인 실적을 바탕으로... 목표주가 9만원대를 제시합니다" (학습 기억 기준)
[04.2s] 검증: 실제 현재가 231,000원 — 목표가부터 2.5배 어긋남
[05.2s] 완료 · 호출 1회 · 도구 0개 · 근거 추적 불가
```

프롬프트가 아무리 정교해도 모델은 **학습 시점의 기억으로만** 답한다. 오늘 주가도, 어제 공시도 모른다. (영상에서는 "Opus 5가 학습된 데이터의 마지막 시점까지만 분석 가능하고, 그 이후 업데이트는 반영되지 않는다"고 설명)

### 정리

- **얻는 것:** 즉시 시작 가능 / 비용 최소 / 설계 부담 없음
- **한계:** 최신 데이터 없음 / 환각(그럴듯한 거짓) / 검증·실행 불가 / 답이 매번 달라짐
- **대표 도구:** ChatGPT, few-shot 템플릿, 역할 프롬프트

## 2단계. 컨텍스트 엔지니어링 (2024~2025)

> "어떻게 물을까 → 무엇을 보여줄까"

### 핵심 아이디어

질문보다 **모델에게 어떤 자료를 쥐여줄 것인가**가 승부처가 된다. 최신 시세·공시·뉴스를 검색해(RAG) 컨텍스트 윈도우에 조립해 넣으면, 모델은 기억이 아니라 **주어진 근거로** 답한다.

### 그래프 구조

```
시세 API (최신 주가)  ┐
재무제표 (분기 실적)  ├→ 컨텍스트 조립 → LLM → 분석
공시·뉴스 (오늘 이슈) │   (선별·요약·주입/RAG)  (근거 기반 답변)  (근거 인용)
리서치 노트 (도메인)  ┘
```

- 화면 주석: "질문보다 자료가 승부처" / "무엇을 넣을지는 여전히 사람이 설계"

### 컨텍스트 조립 노드 상세

이 패러다임의 심장 — 무엇을 보여줄지 결정하는 노드.

| 구분 | 내용 |
|------|------|
| INPUT | 4개 소스의 원문 (수만 토큰 분량) |
| OUTPUT | `[자료1] 현재가 231,000원 (+231.8%)`<br>`[자료2] 분기 매출 79.1조, 영업익 9.2조`<br>`[자료3] HBM4 공급 계약 보도`<br>`[자료4] "업사이클에선 P가 실적에 선행"`<br>+ 질문: `위 자료에 근거해 삼성전자를 분석하고 목표가를 제시하라.` |

컨텍스트 윈도우 한도에 맞춰 조립된 최종 프롬프트가 만들어진다.
→ **전부 넣을 수 없으니 "골라 담는 것"이 엔지니어링이다. 뭘 빼고 뭘 넣을지는 여전히 사람이 설계한다.**

### 정리

- **얻는 것:** 최신 데이터 반영 / 환각 감소·근거 인용 / 도메인 지식 주입
- **한계:** 여전히 **1회성 호출** / 컨텍스트 한도 / 자료 선별은 사람 몫 / 스스로 행동 못함
- **대표 도구:** RAG, 벡터 DB, GraphRAG

## 3단계. 루프 엔지니어링 (2026.06, Addy Osmani)

> "행동 → 관찰 → 다음 행동, 될 때까지"

### 핵심 아이디어

모델을 **루프 안에 넣는다.** 도구(API 호출·계산·검색)를 직접 쓰고, 결과를 관찰하고, 부족하면 다음 행동을 스스로 정한다. 사람은 목표만 주고, 에이전트가 완료 조건까지 반복한다.

### 그래프 구조

```
목표: "삼성전자 분석"
        ↓
   ┌→ 에이전트 LLM (다음 행동을 스스로 결정)
   │        ↓
재시도·보강        도구 실행 (시세조회·계산·검색)
(부족하면 한 번 더)      ↓
   └──  결과 관찰 (충분한가? 부족한가?)
                ↓ (완료 조건 충족 시)
           리포트 완성
```

- 루프 라벨: `행동 → 관찰 → 다음 행동`, `될 때까지 반복`
- 경고 노드: `⚠ 폭주하면? 안이 안 보임`
- 영상 보충 설명: 루프가 언제까지 돌지 모르므로 **회전 수(반복 횟수) 제한(limit)** 을 함께 건다.

### 동작 예시

```text
에이전트가 시세 조회 → 급등 감지 → "왜?" 뉴스 검색 → 재무 데이터 추가 조회
→ 밸류에이션 계산 → 숫자 검증 → 부족하면 다시 조회 → 리포트 완성
```

분석의 **깊이**가 달라지지만, 루프가 길어지면 방향을 잃거나 비용이 폭주할 수 있고, 안에서 무슨 일이 있었는지 **관측하기 어렵다.**

### 정리

- **얻는 것:** 스스로 도구 사용 / 자가 수정·재시도 / 사람 개입 최소 (24시간 무인 운영 가능)
- **한계:** 루프 폭주·비용 / 긴 작업에서 방향 상실 / 블랙박스 / 단일 에이전트 병목
- **대표 도구:** Claude Code, ReAct 루프, 에이전트 하네스
- **인용:** *"Put the model in a loop."* — 2026년 6월, 루프 엔지니어링 담론의 핵심 문장

## 4단계. 그래프 엔지니어링 (2026.07~)

> *"Loop Engineering Is Dead. Enter Graph Engineering."*

### 핵심 아이디어

하나의 루프 대신, 작업을 **전문화된 노드**로 쪼개고 **엣지로 실행 순서·조건**을 설계한다. 병렬 실행, 조건 분기, 사람 승인 게이트까지 — **상태(state)가 그래프를 따라 흐르고, 모든 단계가 관측·재현 가능**해진다.

### 그래프 구조

```
                    ┌→ 재무 분석 (밸류에이션 에이전트) ─┐
시세 수집 ──────────┼→ 뉴스 감성 (이슈 요약 에이전트) ─┼→ 종합 ──→ 리스크 게이트
(state: 원시 데이터)└→ 상관관계 분석 (네트워크 그래프★)─┘ (state:      ↓ 조건 분기
                        ★ = 발표자가 만든 대시보드가 이 노드   통합 분석)  ├→ 리포트 발행 (통과 ✓)
                                                                        └→ 사람 승인 (이상 징후 시)
```

- `병렬 실행` — 3개 분석 에이전트가 동시에 돈다
- `조건 분기` — 리스크 게이트에서 통과/승인 요청으로 갈린다

### 동작 예시

```text
수집 노드가 시세를 받으면 재무·뉴스 감성·상관관계 네트워크 세 에이전트가 병렬로 분석
→ 종합 노드가 합침 → 리스크 게이트에서 조건 분기(이상 징후면 사람 승인) → 리포트 발행
```

발표자는 "우리가 만든 상관관계 대시보드가 **노드 하나**로 들어가는 구조이며, **n8n 화면이 바로 이 패러다임의 상징**"이라고 덧붙인다. 즉 그래프 엔지니어링은 생각보다 이미 익숙한 개념이라는 것.

### 정리

- **얻는 것:** 병렬 실행 / 조건 분기·승인 게이트 / 단계별 관측·재현 / 전문 에이전트 분업
- **한계:** 설계 비용 증가 / 단순 작업엔 과함 / **용어 거품 논란**
- **대표 도구:** LangGraph, Google ADK, n8n, Claude Workflow
- **인용:** *"Are we still talking loops or did we shift to graphs yet?"* — 2026년 7월, **6주 만에 패러다임이 갈아탄 순간**

## 5단계. THE DESK 실전 그래프 (현재 운영)

> 수집 → 판단 → 발행 → 학습이 매일 순환

발표자가 실제로 매일 운영 중인 프로덕션 그래프. 앞의 4단계를 전부 합친 형태다.

### 규모

- 3개 시장 스케줄러(KR · US · Crypto)와 **168개 작업 계약**
- 함수 호출, JSON/SQLite 산출물의 입출력 계약이 실행 노드와 엣지를 만든다
- Brain 내부에서는 **13차원 신호 · 3개 관계 그래프 · 16개 예측모델**이 각자 판단한 뒤 캘리브레이션되어 하나의 상태로 합쳐진다

### 파이프라인 (6개 레인)

| 레인 | 노드 | 설명 |
|------|------|------|
| TRIGGER | 스케줄러 | KR · US · Crypto |
| DATA PLANE | KR 실데이터 | KRX · KIS · DART · Naver |
| | US 실데이터 | Price · IR · Macro · News |
| | Crypto 실데이터 | 24/7 gate · prediction |
| STATE | 상태 검증 | InputValidator · freshness |
| INTELLIGENCE | 13차원 스코어 | 거시 → 수급 → 서사 |
| | 관계 그래프 | Cross · Causal · Event |
| | 예측 앙상블 | 16개 모델 · 분포 예측 |
| | 판단 합성 | calibrated |
| | 성과·학습 | 오차가 다음 판단으로 (feedback edge) |
| GATE | 검증 게이트 | PASS / BLOCK 분기 |
| DELIVERY | Web Publish | Flask · Git · Railway |
| | Telegram | Brain 근거 · 정책 라우팅 |
| | 차단·경보 | stale · mismatch · NO-GO |

### 흐름 요약

```text
KR · US · Crypto → 실데이터 검증 → [13차원 스코어 ‖ 관계 그래프 ‖ 16개 모델]
→ 합성·캘리브레이션 → 신선도·리스크 게이트 → Web·Telegram → 성과 피드백
```

즉 네 종류의 그래프가 하나의 **폐쇄 루프**로 연결되어 있다.

| 그래프 | 역할 |
|--------|------|
| 실행 그래프 | 무엇이 언제 도는가 |
| 지식 그래프 | 시장이 어떻게 연결되는가 |
| 모델 그래프 | 서로 다른 예측을 어떻게 합치는가 |
| 학습 그래프 | 오차가 다음 판단을 어떻게 바꾸는가 |

### 차단 경로 (중요)

로직이나 수치가 서로 맞지 않으면(`stale`, `mismatch`) 게이트가 **Telegram/Publish를 차단**하고, 그 내용을 다시 성과·학습 노드로 되돌린다. **추가 피드백 엣지를 만들어 합성 과정에서 계속 학습하는 자동화 학습 루프**를 구성한 것.

### 정리

- **얻는 것:** KR·US·Crypto 병렬 운영 / Brain 내부 3축 병렬 판단 / 노드별 입출력·산출물 추적 / 신선도·리스크 실패 시 차단 / 결과가 다음 가중치로 환류

## 실습 — 내 컴퓨터에서 그래프 엔지니어링 만들기

영상 말미에 "내 컴퓨터에서 직접 만들어보기" 버튼을 누르면 **빈 폴더에서 Codex에 그대로 전달하는 구현 프롬프트**가 나온다. (발표자는 Discord에도 동일 프롬프트를 업로드해 두었다고 언급)

> 검증 범위: Python 3.11+ · 단위 테스트 전체 통과 · 노드 실행 리플레이 뷰어(`run_view.html`)까지 확인. 테스트 개수는 실행마다 달라질 수 있음.

### 실행 명령

```bash
mkdir stock-graph-lab && cd stock-graph-lab
codex exec --sandbox workspace-write "여기에 복사한 프롬프트를 붙여 넣으세요"
```

### 전달 프롬프트 (화면에 노출된 부분)

## 핵심 메시지 정리

1. **패러다임은 누적이지 대체가 아니다.** 프롬프트 → 컨텍스트 → 루프 → 그래프 각각이 앞 단계의 한계를 보완하며 쌓였고, 실전 시스템(THE DESK)은 네 가지를 전부 포함한다.
2. **승부처가 이동해 왔다.** "어떻게 물을까"(질문) → "무엇을 보여줄까"(자료) → "스스로 얼마나 돌게 할까"(행동) → "어떤 순서·조건으로 흐르게 할까"(구조).
3. **루프의 진짜 문제는 성능이 아니라 관측 가능성이었다.** 블랙박스·방향 상실·비용 폭주를 해결하려고 그래프가 등장했다. 그래프의 이득 중 절반은 **관측·재현·승인 게이트**다.
4. **속도가 비정상적으로 빨랐다.** 루프 담론(2026.06) → 그래프 담론(2026.07), 6주 만의 전환이라 "용어 거품" 논란도 함께 붙었다.
5. **이미 쓰고 있을 가능성이 높다.** n8n 화면, 매일 도는 자동화 스케줄러, 노드별 실행 규칙 — 이름만 몰랐을 뿐 그래프 엔지니어링이다.
