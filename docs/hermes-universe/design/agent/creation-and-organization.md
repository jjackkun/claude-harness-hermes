# 에이전트 생성과 조직 정의 — 입사·소환·수습 기간·담당 찾기

> 작성일: 2026-09-15
> 목적: 에이전트가 언제 어떻게 만들어지고 불리는지, 그리고 조직 구조를 누가 정하는지 정한다.

## 개요

- **입사는 사람이 결정한다.** 사람이 자연어로 입사시키거나, 일을 시켰는데 담당이 없을 때 기계가 사람에게 묻는다. 자동 생성은 설치 시 기본 에이전트 `main`뿐이다.
- 새 에이전트는 **수습 기간**으로 시작하고, 정식 전환은 사람이 판단한다.
- **공장은 조직 구조를 정하지 않는다.** 공장은 틀과 템플릿만 주고, 조직의 축(부서·직무·직급·도메인 등)과 값은 각 소우주가 정한다.

## 1. Claude Code에서 에이전트의 실체

| 지금 있는 것 | 실체 | 이 설계에서의 자리 |
|---|---|---|
| `assets/agents/*.md` 15개(code-reviewer, planner, tdd-guide 등) | 역할 정의 파일. 부를 때마다 백지에서 시작 | 우주 공통 **직무 템플릿** |
| 하위 에이전트 호출, `claude -p` 실행 | 한 번 돌고 끝나는 실행 | **소환** |
| 없음 | 계속 이어지는 개인 | **정체성**: `.hermes/agents/<agent_id>/` |

개인 에이전트는 정체성 폴더를 가지고, **소환될 때마다 그 폴더를 읽고 출근하는 존재**다. 실행은 매번 새로 뜨지만 읽는 기억이 이어진다.

> 읽는 주체는 세션 시작 훅 `claude-sessionstart-agent-soul.sh` 다 — `HERMES_AGENT_ID` 가 있고 정체성 폴더가 있으면 SOUL.md·MEMORY.md(각 4,096 B 상한, 넘치면 잘라 원문 경로를 남김)를 세션 문맥에 넣는다. retired 는 넣지 않는다. 계획 4 에서 빠졌던 부분을 계획 `2026-09-17-summon-soul-injection` 이 채웠다.

> 현재 15개 직무 템플릿은 모두 개발·검토 직무다. 여기서 `planner`는 구현 계획 담당이지 서비스 기획자가 아니다.

## 2. 생성과 소환 (합의, C-01)
| | 생성 (입사) | 소환 |
|---|---|---|
| 무엇 | 명부 등록 + SOUL.md + id 발급 | 일 한 건에 기존 에이전트를 부름 |
| 빈도 | 드묾 | 매 작업 |
| 기록 이벤트 | `agent.created` | `task.assigned` |
| 자동 여부 | 설치 시 `main`만 자동 | 자동이 기본 |

일이 들어오면 **먼저 맞는 기존 에이전트를 찾아 소환한다.** 없을 때만 입사 여부를 사람에게 묻는다.

## 3. 입사 경로 (확정, C-03)
| 경로 | 예 | 결과 | 명령 |
|---|---|---|---|
| 사람이 먼저 입사시킴 | "users 도메인 담당 에이전트 입사시켜" | 수습 기간으로 생성 | `hermes-agent.py hire <이름> --org … [--template …]` |
| 일을 시켰는데 담당이 없어 문의 | 5절 흐름 | 사람이 승낙하면 수습 기간으로 생성 | 같은 `hire` |
| 소우주 설치 | — | `main`만 자동으로 정식 생성. 기록 주체 `system:installer` | 설치기 |

> 폐기: "맞는 직무의 에이전트가 없으면 수습 에이전트를 자동 생성"은 사람에게 문의하는 방식으로 바뀌었다.

### 사람 대면 CLI (확정, C-19)
| 명령 | 하는 일 | 상태 전이 |
|---|---|---|
| `hermes-agent.py hire <이름> --org <discipline,rank,unit> [--template <직무>]` | 명부 등록 · id 발급 · 정체성 폴더 생성 · `agent.created` 기록 | → `probation` |
| `promote <이름>` | 정식 전환 | `probation` → `active` |
| `retire <이름>` | 은퇴(소프트, 4절) | `probation` · `active` → `retired` |
| `rehire <이름>` | 복직 | `retired` → `active` |
| `list` | 명부 보기(상태 · 조직 값) | — |
| `whoami` | 현재 세션의 행위자(`HERMES_AGENT_ID` 없으면 `main`) | — |

- `hire` 가 만드는 폴더: `.hermes/agents/<agent_id>/{SOUL.md,MEMORY.md,skills/}`. SOUL.md 는 공장 틀(`assets/templates/agent/SOUL.md`)에서 머리말을 채워 만든다.
- 사람만 부른다. 자연어("users 담당 입사시켜", "이 일 QA 한테 넘겨")는 스킬 `hermes-agent` 가 이 명령으로 안내한다. 요청 문장을 축 값으로 판별하는 모델 호출은 두지 않는다 — 에이전트가 인자를 채우고, 매칭 결과는 `task.assigned` 에 남겨 나중에 대조한다.

## 4. 수습 기간 (확정, C-04 · C-10 · RV-17)
- 입사를 사람이 결정하므로, 수습 기간은 승인 대기가 아니라 **일을 맡겨 보며 확인하는 기간**이다.
- 수습 기간에도 일을 하고, 이력은 자기 id로 쌓인다.
- 정식 전환은 사람이 판단한다. 참고 자료로 작업 이력의 **주장과 검증 차이**(성공이라 했는데 테스트가 실패한 횟수)를 보여 줄 수 있다.
- 시스템 상태는 조직 직급과 **칸과 이름을 분리**한다(합의). 사무 조직의 직급 "수습사원"과 섞이지 않게 하기 위해서다.

| | 시스템 상태 `status` | 조직 직급 |
|---|---|---|
| 값 | `probation`(수습 기간) → `active`(정식) → `retired`(은퇴) | 소우주 정의 (예: 수습사원 → 주임 → 대리 → 과장) |
| 누가 정하나 | 공장(고정) | 소우주 |

- 승인되지 않은 채 오래 방치된 수습 에이전트의 은퇴 기간은 근거 있는 값이 없어 미정이다.

> ✅ 리뷰 확정 (2026-09-15, RV-17) — 은퇴와 복직 (근거: cumora K-8). 은퇴(`retired`)는 소프트 상태다: 명부에 남고, 기억 · 이력 · 개인 스킬은 지우지 않으며, 소환 대상과 담당 매칭에서만 빠진다. 사람 승인으로 `active` 에 복귀할 수 있고 id · 기억 · 이력이 그대로 이어진다. cumora 는 오프보딩을 `departed_at` 표시로만 하고 `rehire` 하면 기억과 기록이 그대로 돌아온다(`server/src/api/router.ts` `DELETE /agents/:id`, `POST /agents/:id/rehire`). "은퇴한 이름은 같은 소우주에서 재사용하지 않는다"([identity.md](identity.md) 2절)는 복직을 가능하게 하는 규칙이기도 하다 — 이름이 새 에이전트에게 갔으면 돌아올 자리가 없다.

## 5. 일을 시켰을 때 담당을 찾는 흐름 (확정, C-03 · C-05 · C-11)
zeroday-frontend의 실제 구조(도메인은 `src/features/<도메인>/`, 공통 컴포넌트는 `src/components/shared/`의
`BaseInput`·`BaseInputDate`·`BaseCheckbox` 등, `users` 도메인 폴더는 아직 없음)를 예로 든다.

```text
사람: "users 도메인 작업하자. 공통 인풋 텍스트 컴포넌트도 만들어"
  │
  ① 요청을 소우주 조직 정의의 축 값으로 판별
  │   ├─ users 도메인 화면 작업
  │   └─ 공통 컴포넌트 작업
  │
  ② 명부에서 담당 찾기 (구체적인 담당 → 공통 담당 순)
  │
  ├─ users 담당 없음 → 사람에게 문의
  │    "users 도메인을 맡은 에이전트가 없습니다. 입사시킬까요?"
  │      ├─ 입사        → 사람이 이름을 짓고 수습 기간으로 생성
  │      ├─ 이번엔 main  → main 이 수행 (actor = main)
  │      └─ 담당 두지 않음 → 기억해 두고 이 영역은 다시 묻지 않음
  │
  └─ 공통 컴포넌트 담당 확인
       ├─ 있음 → users 담당이 공통 담당에게 요청 (task.handoff)
       └─ 없음 → 사람에게 문의
```

- users 담당은 공통 컴포넌트를 **쓸 수는 있지만 고치지 않는다.** 여러 영역에 영향 가는 변경은 그 영역 담당이 책임진다. 요청 형식은 인계 계약(Q-2)에서 다룬다.
- **사람이 없는 세션**(헤드리스 루프, 백그라운드)에서는 물을 사람이 없으므로 `main`이 수행하고 "담당 없음" 제안을 기록한다. 다음 대화형 세션에서 문의한다(합의).

## 6. 조직 정의는 소우주가 (확정, C-09)
### 왜 공장이 정하면 안 되나

프로젝트 안에 무엇이 있는지 공장은 알 수 없다.

- 한 프로젝트에 기획 · 디자인 · 퍼블리싱 · 프론트엔드 · 백엔드 · QA · QC가 모두 있을 수 있다.
- 사무 회사 프로젝트라면 부서와 대리 · 과장 · 주임 · 수습사원 같은 직급이 있을 수 있다.
- 한 역할도 "공통 기획자"와 "특정 부분 기획자", "번역가"와 "일본어 번역가"처럼 나뉜다.

> 폐기: 논의 중 "직무 · 도메인 · 산출물 세 축"을 고정하려 했다. 그러나 이것도 제품 개발 조직을 전제한 추측이었다. 또 저장소 이름(zeroday-frontend)만 보고 "API 개발자는 백엔드 소우주에 속한다"고 단정했는데, 이 전제는 틀렸으므로 철회했다.

### 틀은 하나 — 직군 · 수직 · 수평 (확정, C-17)
어떤 조직이든 에이전트가 갖는 것은 세 가지뿐이다. **어떤 일을 하는가(직군), 누구 위·아래인가(수직), 누구와
나란히인가(수평).** 그래서 공장이 주는 틀은 하나다. **축의 종류는 공장이 셋으로 고정하고, 각 축에 무엇을 넣을지만
소우주가 정한다.**

| 축 | 뜻 | 제품 개발 조직 | 사무 회사 | 혼자 쓰는 소우주 |
|---|---|---|---|---|
| **직군** `discipline` | 어떤 일을 하는가 | 기획 · 디자인 · 퍼블리싱 · 프론트엔드 · 백엔드 · QA · QC | 총무 · 회계 · 영업 | (비움) |
| **수직** `rank` | 누가 누구를 지시·승인하는가 | 리드 → 담당 | 과장 → 대리 → 주임 → 수습사원 | 사람 → `main` → 나머지 |
| **수평** `unit` | 누구와 같은 단위에 속하는가 (도메인, 팀, 부서) | users · settlement · 공통 | 회계 부서 · 영업 부서 | (비움) |

- **수직 축의 맨 위는 항상 사람이다.** 허가 · 입사 · 조직 단위 생성이 모두 사람 권한이기 때문이다. 공장이 고정한다.
- 직급이 없는 조직은 수직 축을 "사람 → `main` → 나머지" 한 단으로 비워 둔다.

앞서 따로 두려던 것들이 이 틀 안으로 들어온다.

| 따로 두려던 것 | 틀에서의 자리 |
|---|---|
| `match_order`(담당 찾기) | 직군 → 수평 순으로 좁힘 |
| `approval`(허가 권한) | 수직 축 그 자체 |
| `skill_owner_axis`(스킬 3층) | 수평 축의 단위 |
| 팀 · 부서 만들기 | 수평 단위 하나 추가 (사람이) |
| 인계 방향(Q-2) | 위→아래 **지시**, 같은 수평 단위 안 **협업**, 다른 수평 단위로 **요청** |

### 공장이 고정하는 것 vs 소우주가 정하는 것

| 공장이 고정 | 소우주가 정의 |
|---|---|
| 에이전트 id(불변), 이름 | 직군 축의 값 |
| 상태 `probation` / `active` / `retired` | 수직 축의 값(사람이 맨 위인 것만 고정) |
| 명부 등록, 행위자 형식 `human:`·`agent:`·`system:` | 수평 축의 값과 각 단위의 영역·산출물 위치 |
| 세 축의 **종류**, 담당 매칭 · 허가 · 인계의 **규칙** | — |

공장 코드에는 "백엔드", "대리" 같은 조직 단어가 들어가지 않는다.

### 조직 정의 파일 (확정 스키마, C-09 · C-17 — G-14 닫힘)

파일은 `<소우주>/.hermes/organization.yaml` 하나이고 git 추적된다([identity.md](identity.md) 6절).

| 키 | 형식 | 규칙 |
|---|---|---|
| `discipline` | 평면 목록 | 비울 수 있다 |
| `rank` | 평면 목록, 위에서 아래 순 | 맨 위 `human` 은 **기계가 고정**한다 — 파일에 적지 않아도 검증기가 앞에 붙이고, 다른 값을 맨 위에 두면 거부한다 |
| `unit` | 2단 맵 `<이름>: {unit_id, code}` | `unit_id` 는 불변 UUIDv7. 없으면 검증기가 부여해 파일에 써 넣는다. `code` 는 경로 glob 목록(선택) |

제품 개발 프로젝트:

```yaml
discipline: [기획, 디자인, 퍼블리싱, 프론트엔드, 백엔드, QA, QC]
rank:       [리드, 담당]                 # 위에서 아래 순. 맨 위 human 은 기계가 붙인다
unit:
  users:   {unit_id: <UUIDv7>, code: [src/features/users/**]}
  공통:    {unit_id: <UUIDv7>, code: [src/components/shared/**]}
```

사무 회사 프로젝트:

```yaml
discipline: [총무, 회계, 영업]
rank:       [과장, 대리, 주임, 수습사원]
unit:
  회계부:  {unit_id: <UUIDv7>}
  영업부:  {unit_id: <UUIDv7>}
```

- **YAML 부분집합만 허용한다:** 스칼라 · 평면 목록 · 2단 맵. 앵커 · 별칭 · 다중 문서 · 블록 스칼라는 거부한다. 표준 모듈에 YAML 이 없고 헤르메스는 pip 의존을 두지 않으므로 **자체 파서**로 읽는다(cumora `parseSkillMd` 와 같은 태도).
- 에이전트는 경로를 직접 적지 않고 **세 축의 값**만 가진다. 영역과 경로의 연결은 수평 단위에 한 번만 적어, 폴더 구조가 바뀌어도 에이전트 정의를 고치지 않는다.
- 단위 이름을 바꿔도 `unit_id` 가 같아 그 단위의 스킬(`.hermes/units/<unit_id>/skills/`)과 이력이 끊기지 않는다.
- 저장소 밖 산출물(예: 디자인 도구 파일)과 경로가 없는 일(문서 정리, 배포 설정)의 담당 표현은 미정이다.

### 담당 매칭 규칙 (합의, C-11)
1. 요청에 맞는 직군 · 수평 값을 가진 에이전트를 찾는다.
2. **더 많은 축이 맞는 에이전트를 먼저 고른다.** 예: "users 기획자"가 "공통 기획자"보다 먼저. CODEOWNERS나 CSS에서 더 구체적인 규칙이 이기는 것과 같은 원리다.
3. 없으면 사람에게 문의한다.

### 공장의 조직 템플릿 (확정, C-09 · C-18)
| 템플릿 | 파일 | 직군 | 수직 | 수평 |
|---|---|---|---|---|
| 제품 개발 조직 | `assets/templates/organization/product.yaml` | 기획 · 디자인 · 퍼블리싱 · 프론트엔드 · 백엔드 · QA · QC | 리드 → 담당 | 도메인 |
| 사무 조직 | `assets/templates/organization/office.yaml` | 부서 업무 | 과장 → 대리 → 주임 → 수습사원 | 부서 |
| 빈 조직 | `assets/templates/organization/empty.yaml` | (비움) | 사람 → `main` | (비움) |

- **설치 시 `.hermes/organization.yaml` 이 없으면 `empty.yaml` 을 자동 복사한다.** 이미 있으면 건드리지 않는다. 다른 템플릿을 고르거나 고쳐 쓰는 것은 사람이 나중에 한다 — 설치가 조직 선택을 묻지 않는다.
- 템플릿 파일에는 값만 있고 규칙은 없다. 세 템플릿 모두 위 스키마 검증을 통과해야 한다.
- 템플릿은 우주 공통이고, 채택해 고친 조직은 소우주의 것이다. 쓸모 있는 수정은 스킬처럼 이슈로 제안해 우주 템플릿으로 올릴 수 있다.

## 7. 조직 단위와 스킬 세 번째 층 (확정, C-12 · C-13)
- 스킬의 세 번째 층은 고정 이름 "팀"이 아니라 **소우주 조직 정의의 수평 축 단위**다. 수평 축을 비워 두면 이 층을 건너뛴다(소우주 공통 → 개인). 자세한 층 규칙은 [skill-layers.md](../world/skill-layers.md).
- 조직 단위는 스킬 허가 권한을 가지므로 **사람이 만든다**(조직 정의 파일 수정). 에이전트는 "이 단위를 만들자"는 제안만 할 수 있다(합의).
- 조직 단위에도 불변 id(`unit_id`, UUIDv7)를 둔다. 이름을 바꿔도 그 단위의 스킬과 이력이 끊기지 않게 하기 위해서다(6절 스키마).

## 8. 같은 에이전트의 동시 소환 (확정, C-14)
같은 에이전트를 한 컴퓨터에서, 또는 여러 컴퓨터에서 동시에 부를 수 있다. 이것이 가능하도록 기억을 추가 전용
이벤트로 저장한다. 자세한 내용은 [memory-events.md](memory-events.md).
