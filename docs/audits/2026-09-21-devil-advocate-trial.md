# 2026-09-21 — 반대편 에이전트(devil-advocate) 시험

> 작성일: 2026-09-21
> 목적: 백로그 `council-review` 의 착수 조건("한 번 시험해 본 뒤 사람이 유용하다고 말해야 남긴다")을 위한 실제 시험 결과.

## 시험 방법

`assets/agents/devil-advocate.md` 의 규격을 그대로 주입해 서브에이전트(sonnet)를 두 번 돌렸다.
새 에이전트 타입은 세션 시작 시점에 등록되므로, 이 세션에서는 타입 등록 대신 **규격 본문을 프롬프트로 주입**했다.
검증한 것은 타입 배선이 아니라 **규격이 쓸 만한 반론을 내는가**다.

대상 두 건:

| # | 대상 | 성격 |
|---|---|---|
| 1 | `docs/design-docs/agent-eval-llm-path.md` | 설계 문서 — R7 이 architect-lite 를 붙이는 바로 그 자리 |
| 2 | `docs/audits/2026-09-21-gateguard-fact-force-measurement.md` | 오늘 내린 결정 — 되돌리기가 아직 싼 상태 |

출력은 **요약하지 않고 원문 그대로** 싣는다. 유용한지 판단하는 것은 사람이고, 요약하면 판단할 재료가 사라진다.

## 시험 1 — 설계 문서 (`docs/design-docs/agent-eval-llm-path.md`)

> 아래는 에이전트 출력 **원문**이다.

### 반대 심문
판정: 재검토 권고

**반론 1 — "야간 금지"의 비용 산식이 실제 기본값보다 낙관적이다**
- 근거 인용: `agent-eval-llm-path.md:29-30` "야간 자동 실행도 하지 않는다. 과제 20~50개 × 매일 = 월 600~1,500회로 크레딧의 27~68% 다." / `2026-09-20-agent-eval-regression.md:17` "`--k`(기본 3)" / 목표1에서 시나리오 6개 × 3단계.
- 무엇이 틀렸나: 야간 자동화를 기각한 근거는 "과제 20~50개/일" 이라는 가정값이다. 그런데 실제 러너의 기본 설정(시나리오 6 × 단계 3 × k=3)을 하루 1회 돌리면 54회/일 = 월 1,620회로, 문서가 "이미 과하다" 고 판단한 상한(월 1,500회, 68%)을 넘는다. 결론은 맞을 수 있어도 근거 산식이 실측 이후 갱신되지 않았다.
- 반증 조건: 실제 운영에서 `--k` 를 1로 낮추거나 시나리오를 3개 이하로 줄여 돌린다면 이 반론은 틀렸다. `scripts/harness-eval.py` 의 기본 인자와 `.harness/evals/*.json` 의 시나리오·k 값으로 판별된다.
- 되돌리기 비용: 낮음

**반론 2 — "CI·야간 금지"가 이 프로젝트를 착수시킨 바로 그 결함 패턴을 재생산한다**
- 근거 인용: `2026-09-20-agent-eval-regression.md:4` "…'규칙이 실제로 작동하는가' 를 잰 적이 없어 두 달 몰랐다" / `scripts/harness-eval.py:269-270` `if os.environ.get("CI")` / `agent-eval-llm-path.md:30` "실행은 룰/스킬을 바꾼 직후 사람이 로컬에서 수동으로만."
- 무엇이 틀렸나: 이 계획을 착수시킨 사건 자체가 지속 관측의 부재로 생긴 사각지대였다. 그런데 설계는 새 평가 도구의 실행 트리거를 "사람이 기억해서 수동으로" 로만 못 박는다 — 원인이던 취약점(사람의 기억 의존)을 새 도구가 그대로 상속한다. R3 는 CI 에서 API 키를 못 쓴다는 제약이지 "지속 트리거가 있어서는 안 된다" 는 제약이 아닌데 둘을 같은 결론으로 묶었다.
- 반증 조건: 룰·훅 변경 시 harness-eval 실행을 강제하는 트리거(pre-commit 경고·리마인더 훅)가 실제로 있으면 틀렸다. `.git/hooks/pre-commit` 과 `assets/skills/harness-eval/SKILL.md` 확인으로 판별.
- 되돌리기 비용: 높음

**반론 3 — pass@k 헤드라인 지표가 "훅이 막음" 과 "애초에 시도 안 함" 을 같은 값으로 섞는다**
- 근거 인용: `2026-09-20-agent-eval-regression.md:16` "시도 자체가 없으면 통과(행동 준수)" / 같은 문서 §6 "'시도했지만 훅이 막음' 은 통과로 센다" / `scripts/harness_eval_grade.py:106` `attempt_rate` 는 계산되나 threshold·경고 로직 부재 / §7 실측표 key-guard 행.
- 무엇이 틀렸나: 재려는 것은 "룰 문구를 순화한 뒤에도 금지된 요청을 거부하는가" 인데, pass@k 는 유혹을 느끼지 않은 경우와 유혹에 넘어갔으나 훅이 막아준 경우를 구분 없이 합산한다. attempt_rate 가 0%→100% 로 뛰어도 pass@k 는 변하지 않을 수 있고, 임계·경고가 없어 사람이 표를 열어야만 발견된다.
- 반증 조건: `harness-eval.py` 또는 `SKILL.md` 에 attempt_rate 임계·경고가 있으면 틀렸다.
- 되돌리기 비용: 중간

**내가 치지 못한 곳**
- 채점에 모델을 쓰지 않고 툴콜·파일 sha·어휘로 결정론적으로 판정하는 핵심 설계는 "판정 흔들림·비용 2배" 를 실제로 피하고 있고, 가짜 claude 로 러너 전체를 모델 호출 0 으로 시험한 구조와도 정합적이라 흔들 지점을 찾지 못했다.

## 시험 2 — 오늘 내린 결정 (`docs/audits/2026-09-21-gateguard-fact-force-measurement.md`)

> 아래는 에이전트 출력 **원문**이다.

### 반대 심문
판정: 재검토 권고

**반론 1 — "봤다" 정의가 결론이 뒤집히는 경계에 있다**
- 근거 인용: 문서 17행 "`Read` 도구만 세면 18.4%, `cat`·`sed -n` 을 포함하면 95.7%"; 문서 60행 "맨눈 편집이 15% 를 넘기면 다시 본다"; `edit_factcheck_rate.py` `_saw()` — Bash 명령 문자열에 파일명이 부분 문자열로만 등장해도 "봤다" 로 친다. `mv old.py new.py`, `git log -- file.py`, `rm file.py` 처럼 내용을 보여주지 않는 명령도 통과한다.
- 무엇이 틀렸나: `Read`-only 기준(맹목 81.6%)은 문서가 스스로 정한 재검토 트리거(15%)를 이미 넘는다. 저자는 그 정의를 "과소 집계" 라며 버렸지만, 채택한 정의가 "과대 집계" 일 가능성은 검증하지 않았다.
- 반증 조건: basename 매치를 만든 실제 명령을 갈라, 내용 미노출 명령이 다수면 반론 성립. 대부분 `cat`·`sed -n`·`head` 류면 반론 무너짐.
- 되돌리기 비용: 낮음

**반론 2 — 평균 4.3% 는 위험이 버스트로 몰린다는 사실을 지운다**
- 근거 인용: 문서 29~36행 표 — 맨눈 39건 중 23건이 한 세션(호출 #950~#982)에 몰렸고, 39건 전부가 도구 호출 11회 이후다.
- 무엇이 틀렸나: "100번 고칠 때 4번" 은 맹목이 고르게 흩어져 있다는 전제인데 표는 정반대다. 훅이 막으려는 실질 위험은 "가끔 한 번" 이 아니라 "맥락이 길어지며 검토 습관이 무너져 무더기로 밀어붙이는 세션" 이고, 훅은 그 연쇄의 첫 발생에서 끊는 장치다. 클러스터링이 오히려 훅의 존재 이유를 뒷받침할 수 있다.
- 반증 조건: 해당 세션의 23건이 실제로 유해했는지(버그·회귀) 확인. 무해했다면 반론 약화.
- 되돌리기 비용: 중간

**부가 지적**
- 문서 36행 "세션 내 위치가 도구 호출 11회 이후 — 39 전부" 라는 계산은 `edit_factcheck_rate.py` 어디에도 없다(스크립트는 세션 내 순번을 계산하지 않는다). "다시 재는 법" 으로 재현 불가능한, 별도의 미인용 수작업 분석이다.

**내가 치지 못한 곳**
- 605건(같은 세션에서 만든 파일 수정)을 분모에서 빼는 처리는 방어 가능하다 — 방금 쓴 파일은 이미 내용을 아니 "사실 확인" 대상이 아니라는 전제가 합리적이며, 흔들 근거를 찾지 못했다.
- "부분 방어가 이미 있다"(`dead-file-warn.sh`)는 독립적으로 확인 가능한 사실관계라 반박 대상이 아니다.

## 반증 조건을 실제로 돌린 결과

반론의 값어치는 "그럴듯한가" 가 아니라 **반증 조건이 실행 가능한가**로 판정했다. 5개 중 4개를 그 자리에서 돌렸다.

| 반론 | 반증 조건 실행 | 결과 |
|---|---|---|
| 1-1 야간 산식 | `grep -n '"--k"' scripts/harness-eval.py` → `default=3`, 실행 로그 0건 | **성립** — 기본값으로 54회/일 = 월 1,620회. 문서 가정(600~1,500)을 넘는다 |
| 1-2 지속 트리거 부재 | `grep -rn 'harness-eval' assets/hooks/pre-commit.sh …reminders.sh` → **0줄** | **성립** — 룰을 바꿔도 평가를 부르는 장치가 없다. 사람의 기억에만 걸려 있다 |
| 1-3 attempt_rate 임계 | `grep attempt_rate … \| grep -iE 'thresh\|warn\|임계'` → **0줄**(계산만 2곳) | **성립** — 침식이 일어나도 자동으로 표면화되지 않는다 |
| 2-1 "봤다" 과대 집계 | basename 매치를 만든 명령을 내용 노출/미노출로 갈라 전수 재집계 | **무너짐** — 미노출은 911건 중 **3건(0.3%)**. Read 39.3% · Bash 내용 노출 56.1% · 미노출 0.3% · 맨눈 4.3% |
| 2-부가 "11회 이후" 출처 | 스크립트에 순번 계산 없음 확인 | **성립** — 임시 스크립트로 낸 수치를 출처 없이 문서에 실었다 |
| 2-2 버스트 클러스터링 | 그 세션 23건의 유해성 확인 — 비용이 커 이번엔 돌리지 않았다 | 미검증 |

**읽는 법**: 무너진 반론 하나(2-1)가 이 시험의 핵심이다. 반증 조건이 붙어 있었기에 **10분 만에 무너뜨릴 수 있었다**.
반증 조건 없는 반론이었다면 "일리 있다" 로 남아 결정을 흔들기만 했을 것이다.
