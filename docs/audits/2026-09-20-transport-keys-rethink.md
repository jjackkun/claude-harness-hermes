# 2026-09-20 — 운반·열쇠 재검토: 발전 재료만 평문으로, 읽을 권리는 저장소 접근권

## 실측으로 드러난 문제

1. **올릴 것을 거꾸로 골랐다.** 발전(결정화·드림·강등)에 쓰이는 것은 요약·패턴 수·기억 이벤트·스킬인데, 이 중 요약·패턴 수는 **안 올라간다**(state.db 로컬).
   발전에 다시 쓰이지 않는 대화 원문(`history/`)은 올리기로 했고, 그 때문에 전부 암호화·열쇠가 붙었다.
2. **효과 0.** 열쇠는 사람이 세션 밖에서 만들어야 하니(T-11) 어느 소우주도 켜지 않았다(공장·ai-create·terminal-shipping 모두 sync.json·열쇠·ref 0).
3. cumora·ECC 는 둘 다 대화 원문을 올리지 않는다. ECC 는 저장소에 올릴 기억(프로젝트·팀)과 안 올릴 기억(개인)을 범위로 갈라 올리는 쪽은 평문이다.

## 논의에서 확정한 원칙

- **기억 ≠ 기록.** 사람은 대화를 낱말로 기억하지 않고 요약을 기억한다. 발전에 필요한 것은 요약이고, 원문은 그 컴퓨터의 기록이다. 원문은 옮기지 않는다.
- **읽을 권리 = 저장소 접근권.** 내가 주인이거나 초대받은 조직원이면 그 저장소의 기억은 내 것이다. 비공개 저장소는 평문. 열쇠는 "접근권과 신뢰가 다른 경우" 곧 공개 저장소에서 원문까지 올리려는 사람의 **선택**으로 내려간다.
- **사람 손이 가는 절차를 두지 않는다.** 열쇠 생성도, "내 정보 목록" 도 강제가 되면 켜지지 않는다. 설치기(`setup`·`update-all`)가 판별·설정을 전부 한다.
- **마스킹은 자동, 세 겹.** (1) 생성 단계 치환 — 요약·기억·note 를 쓰는 지시문이 실제 사람 이름·주소·연락처·계좌 등을 역할·종류로 바꿔 쓴다(원문은 요약 때 이미 모델이 본다, 새로 새는 것 없음). (2) 꼴 규칙 — 전화·이메일·주민번호·카드·계좌·한국 주소·알려진 토큰 꼴. (3) 기계가 이미 아는 값 자동 정답지 — `.env` 값, `git config user.name`, 커밋 작성자, 명부 이름, OS 사용자명. 사용자가 관리하는 목록은 없다. 모델에게 "개인정보냐" 를 묻는 방식은 쓰지 않는다(재현 불가·값 유출).
