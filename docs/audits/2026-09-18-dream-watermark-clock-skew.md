# dream 워터마크 시계 역행 — 소우주 실측 (2026-09-18)

> 목적: `backlog/dream-watermark-clock-skew.md` 가 "먼저 잴 것" 으로 정한 실측을 수행하고 우선순위를 정한다.
> 방법: 등록 소우주 12곳 중 `.hermes/state.db` 가 있는 8곳을 읽기 전용(`mode=ro`)으로 조회. 코드 변경 없음.

## 질문

`hermes-dream.py` 는 `session_summary.updated_at > watermark` 로 수집하고 워터마크를 마지막 요약 시각으로 올린다.
벽시계가 뒤로 가면(2026-09-09 시험 덤프에서 실측된 현상) 그 뒤 종료된 세션 요약이 워터마크보다 이르게 찍혀 영구 누락된다.
**운영 DB 에서 실제로 일어났는가?**

## 지표

1. **누락 후보** — 워터마크를 만든 dream 실행(`run_at`) 이후에 갱신됐는데 `updated_at <= watermark` 인 요약 수.
2. **시계 역행** — id 가 단조 증가하는 표에서 시각 열이 앞 행보다 이른 쌍의 수. `dream_log(id, run_at)` 가 유일한 후보다.
   (`session_summary` 는 `ON CONFLICT DO UPDATE` 라 rowid 가 최초 삽입 순서이고 `updated_at` 은 마지막 갱신 — rowid 순
   비교는 의미가 없다. 첫 조회에서 zeroday 70건이 그렇게 나왔고, 원인을 확인한 뒤 지표에서 뺐다.)

## 한계

- dream 실행 간격은 throttle(20h) 때문에 시간 단위라, 초 단위 역행은 `run_at` 비교로 잡히지 않는다. 역행 자체의
  발생 여부는 이 표로 부정할 수 없다 — 다만 **그로 인한 누락**(지표 1)은 0 이 확실하다.
- 요약이 dream 실행과 같은 초에 쓰이면 시계 역행 없이도 누락된다(초 해상도 문제의 일반형). 이번 표는 그 사례도 0 임을 보인다.

## 결정

- 스키마 변경(단조 `seq`)·수집 조건 변경은 **하지 않는다**. backlog 가 정한 규칙("0 이면 우선순위 낮게")대로 backlog 에
  남기고 실측 결과·지표 정의를 붙인다. 재측정 조건: 어느 소우주에서든 누락 후보 ≥ 1.
- 재측정 명령은 backlog 문서에 그대로 둔다(한 번에 8곳을 훑는다).
