# 2026-09-29-skill-yield-integrity — 스킬 주입 기록을 믿을 수 있게 만든다

> 출처: `docs/exec-plans/backlog/skill-correlation-coverage.md`(2026-09-22)를 착수한다. 관련 후보: `backlog/crystallize-stability-score.md` 후보 1(도움 판정의 흔한 낱말 제외).
> 측정일: 2026-09-29, 이 저장소(공장) `.hermes/state.db` 와 `~/.claude/projects/…/*.jsonl`.

## 1. 동기 (Why)

스킬은 사용자 입력마다 주입되고, 세션이 끝나면 "도움이 됐는지"를 재어 쓸모없는 스킬을 강등한다. 이 재는 값이 믿을 수 없다.

측정으로 드러난 사실 셋:

1. **주입 기록의 61% 는 사람의 대화가 아니라 내부 모델 호출이다.** 주입이 있는 세션 890개 중 **865개는 `claude -p` 로 돌린 내부 호출**(요약·판정 등, 진입 `sdk-cli`)이다. 이 호출들은 `HERMES_DISABLED=1` 로 훅을 끄고 도는데, 스킬을 넣는 훅(`claude-userpromptsubmit-dispatch.sh` → `claude-userpromptsubmit-reminders.sh`)은 그 플래그를 보지 않는다. 그래서 내부 호출마다 스킬이 실려 **토큰이 낭비되고**, 원장 4,280줄 중 2,601줄이 잡음이다.
2. **진짜 대화 세션의 판정은 괜찮다.** 사람이 연 세션 25개 중 23개가 판정됐고(92%), Stop 훅이 끝까지 돈 세션은 주입이 있는 23개 모두 판정됐다. 즉 "판정 누락 61%" 의 실체는 내부 호출 잡음이다.
3. **"도움" 이 94% 인 것은 긴 세션 12개에 몰린 수치다.** 판정된 1,679건 중 1,616건이 큰 세션 12개에서 나왔다. 긴 세션은 도구 활동 낱말이 많아 "키워드 2개 겹침" 을 거의 항상 넘는다. 2026-09-22 에 대화 기록이 남은 전체 세션에 같은 규칙을 다시 돌리면 도움은 9% 였다(백로그 §추가 실측). 저장된 값과 전체 재판정이 10배 어긋난다.

부수 발견: 스킬별 "주입 수" 카운터(`skill_index.used_count`)는 색인에 걸린 것만 올려 실제 주입 기록보다 적다(전체 3,719 대 4,280). 판정된 수(도움+소용없음)는 실제 기록 안에 들어가므로 도움이 부풀려진 것은 아니다.

> 여기까지 다시 읽었다: 세 사실이 모두 `skill_injection` 원장과 그 판정에서 나온다. 고칠 대상은 (가) 원장에 무엇이 들어가는가, (나) 판정이 무엇을 "도움" 으로 치는가, (다) 카운터가 원장과 같은 것을 세는가 셋이다.

(스킬, 세션) 쌍은 한 번만 센다. 표본을 세션 id 짝홀로 둘로 나눠 **한쪽에서 규칙을 고르고 다른 쪽에서 확인**한다. 채택 기준은 진짜-가짜 차이가 가장 크되 진짜 도움률이 하한(§6 에서 표로 정한다) 아래로 내려가지 않는 규칙이다. 검증: `python3 scripts/hermes_yield_replay.py --db .hermes/state.db` 의 표와 `bash tests/hermes-yield-integrity-test.sh` §2(가짜 짝이 진짜 짝보다 도움이 적게 나오는 합성 자료).

- 2026-09-29: 판정 규칙은 임계를 먼저 정하지 않고 "진짜 짝 대 가짜 짝" 차이로 고른다 — 근거: 도움률이 94% 인지 9% 인지는 표본에 달렸다(긴 세션 쏠림). 우연히 넘는 정도를 기준선으로 삼아야 임계에 근거가 생긴다.
- 2026-09-29: 규칙 채택은 표본을 반으로 나눠 한쪽에서 고르고 다른 쪽에서 확인한다 — 근거: 후보 네 개를 같은 표본에서 고르고 그 표본으로 재면 과적합이다(계획 리뷰).
- 2026-09-29: **판정 규칙은 바꾸지 않는다** — 근거: 재판정 실측(사람 세션 17개·짝 260개, 도구 안 쓴 세션 제외) 결과 현재 규칙은 진짜 짝 0.98 대 가짜 짝 0.91(차 +0.07)이라 "도움" 표시가 거의 정보가 없다. 후보 13종 중 전체 합계로는 `흔한낱말제외50%+비율>=0.1` 이 +0.35(even +0.43, odd +0.24)로 낫지만, 중간 세션(100~999 낱말, 짝 67)에서 진짜율이 0.04 로 무너져 가짜(0.42)보다 낮다 — 스킬 키워드가 중앙값 67개·최대 1,015개로 길어 짧은 세션이 비율을 못 채운다. 어떤 후보도 세 층에서 동시에 진짜>가짜가 아니다. 손해: 도움/소용없음 누계는 계속 믿을 수 없다(강등은 `도움=0` 이 조건인데 도움이 거의 안 0 이라 사실상 안 일어난다). 되돌리는 법: 표본이 커지면 `python3 scripts/hermes_yield_replay.py` 를 다시 돌려 채택 여부를 다시 본다.
- 2026-09-29: 카운터는 원장이 있을 때 `UPDATE … SET used_count = (원장 행 수)` 로 맞춘다(주입 때마다 +1 하지 않는다). 색인 밖 스킬은 카운터 행이 없어 세지 않는다 — 원장에는 남는다(현재 색인 밖 주입 0건). 세션ID가 없어 원장에 못 남길 때만 옛 방식(+1)을 유지한다.
- 2026-09-29: 옛 원장 행 삭제는 미리보기가 기본 — 근거: 삭제는 되돌릴 수 없고, 어느 소우주에 적용할지는 사람이 정한다(옛 원문 삭제 때와 같은 원칙).

## 7. 발견·예외

- 내부 호출이 스킬을 받는 것은 판정만의 문제가 아니라 **매 호출 약 1.5KB 의 낭비**다. 이 저장소에서 865회 × 약 1.5KB ≈ 1.3MB 가 모델 입력으로 나갔다(추정, 주입 훅 로그의 `injected bytes` 평균 기준).
- 전체 시험 1회에서 6개가 깨졌다: `hermes-search.py` 가 501줄이 되어 R-size 에 걸린 연쇄 3개(주석 줄여 500줄로) · 문서 개수 동기화 1개(`sync-doc-counts.sh`) · `hermes-agent-summary-test` 는 제 변경과 무관한 날짜 시한폭탄(고정 날짜 2026-09-29 가 오늘이 되어 깨짐, 2099 로 고침) · `harness-eval-test` 는 다시 돌리니 통과(백로그 `harness-eval-test-flaky.md` 의 그 불안정).
- 안내서 대조: `docs/design-docs/hermes-engineering.md` 에는 `used_count` 컬럼 이름만 있고 판정 규칙·카운터 설명이 없어 고칠 곳이 없다.
- 기억(`memory`)에 "전파는 설치 목록 기준으로도 올린다" 를 적었다. 이번 수정도 훅이라 전파 때 소우주 설치 목록을 함께 봐야 한다.

## 8. 회고

- 잘된 것: 내부 호출 차단(865개 세션의 잡음 원인)과 카운터 단일화를 시험으로 고정했다. 재판정 도구가 "도움" 표시의 정보량이 거의 0 임을 숫자로 보였다.
- 잘못된 것: 처음 재판정은 도구를 안 쓴 세션을 가짜 뽑기 풀에 넣어 가짜율을 0.60 으로 낮게 재고 "현재 규칙 +0.38" 이라 읽었다. 풀을 도구 쓴 세션으로 좁히니 0.91 이 됐다(+0.07). 시험 §2 가 이 풀 오염을 잡는다. 또 시험이 부모 세션의 `CLAUDE_PROJECT_DIR` 때문에 공장 실제 원장에 3행을 남겼다 — 시험 끝의 공장 원장 무변경 확인으로 막는다.
- 다음 룰 후보: 키워드 겹침 대신 다른 신호(스킬 안내를 실제로 따랐는지)를 찾는 계획을 백로그에 둔다. 판정 규칙은 그 신호가 생기기 전까지 강등 근거로 쓰지 않는다.
